# Refactoring 기획 워크플로우

코드 냄새나 막연한 개선 아이디어를 **근거가 있고, 동작을 보존하며, 되돌릴 수 있는 리팩터링 이슈**로 변환하는 파이프라인이다.

이 문서는 `/refactoring-planner` 스킬의 근거 자료다. 스킬은 이 문서의 승인 게이트와 안전 규칙을 축약하거나 생략해서는 안 된다.

---

## 1. 이 워크플로우가 해결하는 문제

리팩터링은 “코드를 예쁘게 정리하는 작업”이 아니다. 다음 변경을 더 안전하고 빠르게 만들기 위해 현재 구조의 마찰을 줄이는 작업이다.

이 워크플로우는 다음 실패를 방지한다.

- 파일이 길다는 이유만으로 근거 없이 분리한다.
- 새 라이브러리를 써보고 싶다는 이유로 구조 전체를 교체한다.
- 기존 동작을 고정하지 않은 채 코드를 이동해 회귀를 만든다.
- 리팩터링과 기능 변경을 한 PR에서 함께 수행해 실패 원인을 알 수 없게 만든다.
- 여러 도메인과 레이어를 한 번에 고쳐 롤백이 불가능해진다.
- “가독성이 좋아졌다”는 주관적 설명만 남기고 효과를 검증하지 않는다.

### 리팩터링의 정의

> 외부에서 관찰 가능한 동작은 유지하면서 내부 구조를 개선하는 변경

동작 변경이 필요하다면 숨기지 말고 별도의 feature 또는 bug-fix 이슈로 분리한다. 불가피하게 함께 진행해야 한다면 리팩터링 커밋과 동작 변경 커밋을 분리하고 각각의 Acceptance Criteria를 둔다.

## 2. 전체 흐름

```text
brief-original.md (문제 제기·관찰·가설)
    ↓ 단계 0 — 범위와 기준선 고정
baseline.md (보존할 동작·현재 품질·검증 명령)
    ↓ 단계 1 — 비판적 구조 진단
diagnosis.md (증상·근본 원인·후보·근거)
    ↓ 단계 2 — 목표 인터뷰와 우선순위 확정
brief-fixed.md (개선 목표·불변 조건·비범위)
    ↓ 단계 3 — 3안 비교 + 라이브러리 도입 심사 + ADR
plan.md (선택한 구조·마이그레이션·롤백)
    ↓ 단계 4 — 회귀 안전망 설계
regression-plan.md (특성화·계약·통합 테스트)
    ↓ 단계 5 — 안전한 체크포인트로 이슈 분해
issues.md + GitHub Issues
    ↓ 각 이슈 구현·검증
result.md (전후 비교·남은 부채·후속 결정)
```

### 기본 디렉터리

```text
docs/refactors/{name}/
├── brief-original.md
├── baseline.md
├── diagnosis.md
├── brief-fixed.md
├── plan.md
├── regression-plan.md
├── issues.md
└── result.md
```

Light 트랙(§2-1)에서는 `brief-original.md`, `baseline.md`(최소), `issues.md`, `result.md`(간단)만 생성하고 나머지는 생략한다.

`{name}`은 해결책이 아니라 문제 영역을 나타내는 kebab-case 이름을 사용한다.

- 좋은 예: `post-reaction-state`, `player-boundary`, `post-persistence-coupling`
- 피할 예: `use-react-query`, `split-files`, `clean-architecture`

해결책을 이름에 넣으면 진단 전에 결론을 고정하게 된다.

## 2-1. 트랙 선택

모든 리팩터링에 7단계 전체를 강제하면 기획 자체가 실제 작업량보다 무거워질 수 있다. 시작 전에 아래 기준으로 Light/Full 트랙을 정한다.

### 판단 기준

| 기준                           | Light 트랙              | Full 트랙                     |
| ------------------------------ | ----------------------- | ----------------------------- |
| 영향 범위                      | 단일 파일/모듈          | 여러 모듈·도메인·앱 경계      |
| 공개 계약(API, DTO, 화면 동작) | 불변                    | 변경 가능성 있음              |
| 라이브러리 도입                | 없음                    | 있음                          |
| 대안 비교 필요성               | 접근 방식이 사실상 하나 | 트레이드오프가 있는 복수 대안 |

네 기준이 모두 Light 쪽이면 Light 트랙을 따른다. 하나라도 Full 쪽에 해당하면 Full 트랙을 따른다. 판단이 애매하면 Full 트랙을 기본값으로 한다.

### 트랙별 게이트 매핑

| 단계            | Full 트랙                      | Light 트랙                                      |
| --------------- | ------------------------------ | ----------------------------------------------- |
| 0. 범위·기준선  | `baseline.md` 정식 작성        | `brief-original.md`에 최소 기준선만 인라인 기록 |
| 1. 구조 진단    | `diagnosis.md` 별도 작성       | 생략 — brief에 한두 문단으로 대체               |
| 2. 목표 인터뷰  | `brief-fixed.md` 별도 작성     | 생략 — Goal/Out of Scope만 brief에 기록         |
| 3. 3안 비교·ADR | `plan.md` 정식 작성            | 생략 — 선택한 접근과 이유만 한 문단             |
| 4. 회귀 안전망  | `regression-plan.md` 정식 작성 | 최소 회귀 체크리스트만(항상 필수)               |
| 5. 이슈 분해    | 여러 이슈로 분해               | 보통 이슈 1개                                   |
| 6. 완료 검증    | `result.md` 정식 작성          | 간단 요약(Before/After 한 단락)                 |

트랙과 무관하게 항상 지키는 것: **Behavior Invariants 기록, 최소 회귀 검증, 롤백 경로 명시.** 이 세 가지는 Light 트랙에서도 생략하지 않는다. Light 트랙은 GATE 1·GATE 2·GATE 3을 생략하고 GATE 0 → GATE 4 → GATE 5 → GATE 6만 거친다.

## 3. 시작 조건

### 필수 입력

- `docs/refactors/{name}/brief-original.md`
- 관련 코드와 테스트
- 프로젝트 지침(`CLAUDE.md`, 컨벤션, 기존 ADR)
- 가능하면 최근 변경 이력과 장애·버그 기록

### `brief-original.md` 최소 형식

```markdown
# 문제 영역

## 관찰한 증상

- 어떤 변경이 어렵거나 반복적으로 실패하는가?
- 어느 파일·모듈·사용자 흐름에서 나타나는가?

## 실제 사례

- 최근 수정·버그·중복·성능 문제의 구체적 예

## 초기 가설

- 원인으로 의심하는 것은 무엇인가?
- 확정 사실이 아니라 가설임을 명시한다.

## 기대 효과

- 이 구조를 개선하면 어떤 다음 변경이 쉬워지는가?

## 제약

- 반드시 유지할 동작, 일정, 호환성, 운영 제약
```

파일이 없다면 코드부터 고치지 않는다. 먼저 사용자가 관찰한 문제를 짧게라도 기록하도록 요청한다.

## 단계 0: 범위와 기준선 고정

### 목적

현재 동작과 품질 상태를 기록해 “리팩터링 전에도 실패하던 것”과 “리팩터링이 새로 깨뜨린 것”을 구분한다.

### 핵심 활동

#### 0-1. 프로젝트 지침과 기존 결정 읽기

다음 순서로 확인한다.

1. `CLAUDE.md`, `README.md`
2. 관련 ADR와 설계 문서
3. 패키지 매니페스트와 실행 스크립트
4. 관련 코드와 테스트
5. 최근 커밋에서 반복적으로 변경된 파일

기존 결정이 있다고 해서 무조건 유지하지는 않는다. 다만 근거 없이 다시 논쟁하지도 않는다. 전제가 바뀌었거나 실제 문제가 확인된 경우에만 새 ADR로 대체한다.

#### 0-2. 외부 관찰 동작과 불변 조건 고정

관련 사용자 흐름, API 계약, 상태 전이, 데이터 저장 규칙을 기록한다.

```markdown
## Behavior Invariants

- 로그인하지 않은 사용자의 공개 피드 접근 결과는 바뀌지 않는다.
- 좋아요 요청 실패 시 화면과 전역 상태가 이전 값으로 복구된다.
- 큐에서 현재 곡을 제거할 때 적용되는 다음 곡 선택 규칙은 유지된다.
- 기존 DTO의 필드명과 optional/nullable 의미는 유지된다.
```

#### 0-3. 기준 검증 실행

VIBR의 기본 검증 후보는 다음과 같다.

```bash
pnpm lint
pnpm check-types
pnpm test
pnpm build
```

모든 명령이 성공한다고 가정하지 않는다. 실행 결과, 실패 항목, 소요 시간을 그대로 기록한다. 특정 앱에 테스트 스크립트가 없다면 그것도 안전망 공백으로 기록한다.

가능하면 다음 기준도 수집한다.

- 핵심 테스트 수와 커버리지
- 번들 크기 또는 빌드 시간
- 대상 API의 응답 시간과 쿼리 수
- 컴포넌트 재렌더 횟수
- 변경 영향 파일 수, 순환 의존성, import fan-in/fan-out

측정할 수 없는 값은 임의의 숫자로 만들지 말고 `측정 불가`와 이유를 쓴다.

### 산출물

- `docs/refactors/{name}/baseline.md`

### 승인 게이트

```text
[GATE 0] 사용자가 대상 범위, 보존할 동작, 기준선의 기존 실패를 확인할 때까지 대기
```

## 단계 1: 비판적 구조 진단

### 목적

“코드가 복잡해 보인다”를 실제 변경 비용을 만드는 구조적 원인으로 좁힌다.

### 진단 원칙

#### 파일 길이는 증거가 아니라 탐색 신호다

긴 파일도 하나의 응집된 책임을 가진다면 나쁘지 않을 수 있다. 반대로 짧은 파일 여러 개가 암묵적 상태와 순환 의존성을 공유하면 더 나쁠 수 있다.

#### 모든 판단에 관찰 근거를 붙인다

근거를 다음 세 등급으로 구분한다.

| 등급       | 의미                         | 예시                                             |
| ---------- | ---------------------------- | ------------------------------------------------ |
| Fact       | 코드·테스트·로그로 직접 확인 | 한 훅이 인증, 폴링, 낙관적 갱신을 모두 수행함    |
| Inference  | 여러 사실에서 도출한 해석    | 독립 테스트와 변경 격리가 어려울 가능성이 큼     |
| Hypothesis | 아직 검증하지 않은 가설      | 서버 상태 라이브러리를 도입하면 중복이 줄어들 것 |

가설을 사실처럼 표현하지 않는다.

#### 증상과 근본 원인을 분리한다

```text
증상: 좋아요 수정 때 피드와 상세 모달을 함께 손대야 한다.
  ↓ 왜?
직접 원인: 서버 상태와 화면별 낙관적 상태가 여러 위치에 존재한다.
  ↓ 왜?
구조 원인: 상태 소유권과 동기화 계약이 명시되지 않았다.
```

### 탐색 항목

1. **책임 응집도** — 한 모듈이 서로 다른 변경 이유를 몇 개 갖는가?
2. **결합도** — 한 변경이 몇 모듈·레이어로 퍼지는가?
3. **상태 소유권** — 같은 사실의 원본이 여러 곳에 존재하는가?
4. **경계 명확성** — UI·도메인·인프라 규칙이 섞였는가?
5. **테스트 이음새** — 외부 효과를 대체하고 핵심 규칙을 독립 검증할 수 있는가?
6. **오류·동시성** — 실패, 재시도, 중복 요청, 순서 역전 규칙이 분산됐는가?
7. **데이터 계약** — DTO, 엔티티, 화면 모델의 역할이 섞였는가?
8. **운영성** — 로그·메트릭·타임아웃·롤백 지점이 있는가?
9. **변경 이력** — 자주 바뀌거나 버그가 반복된 hot spot인가?
10. **죽은 추상화** — 실제 대체 구현 없이 인터페이스와 래퍼만 늘었는가?

### 후보 우선순위

각 후보를 1~5점으로 평가한다. 총점만으로 자동 결정하지 않고 비교 근거로 사용한다.

| 기준          | 질문                                   |
| ------------- | -------------------------------------- |
| 변경 빈도     | 앞으로도 자주 수정될 영역인가?         |
| 결함 위험     | 회귀·동시성·정합성 버그 가능성이 큰가? |
| 영향 범위     | 개선하면 여러 후속 변경이 쉬워지는가?  |
| 근거 강도     | 실제 사례와 코드 증거가 충분한가?      |
| 안전망 가능성 | 동작을 테스트로 고정할 수 있는가?      |
| 구현 비용     | 작은 단계로 나누어 완료할 수 있는가?   |

### YAGNI 질문

> 이 영역에 향후 두세 번의 실제 변경이 없다면 지금 리팩터링할 가치가 있는가?

대답이 `아니오`라면 보류 후보로 남긴다. 미래의 모든 가능성을 위한 범용 구조는 만들지 않는다.

### 산출물

- `docs/refactors/{name}/diagnosis.md`
- 후보별 근거, 우선순위, 보류 이유
- 선택을 권하는 후보 1개와 이유

AI의 추천과 사용자의 최종 선택은 다를 수 있다. 사용자가 추천 후보와 다른 후보를 선택하면, 그 후보를 선택한 근거를 diagnosis.md에 추가로 기록한 뒤 다음 단계로 넘어간다. 최종 선택권은 항상 사용자에게 있다.

### 승인 게이트

```text
[GATE 1] 사용자가 이번 사이클에서 다룰 문제 후보 하나를 선택할 때까지 대기
```

## 단계 2: 목표 인터뷰와 범위 확정

### 목적

선택한 구조 문제를 어떤 품질 속성까지 개선할지 확정한다.

### 질문 방식

AI는 한 번에 질문 하나만 한다. 각 질문에는 추천안과 이유를 포함한다. 문서와 코드에 이미 답이 있으면 다시 묻지 않는다.

### 필수 질문 영역

1. 다음에 쉬워져야 할 **구체적인 변경**은 무엇인가?
2. 절대 바뀌면 안 되는 사용자 동작과 API 계약은 무엇인가?
3. 가장 중요한 품질 속성은 무엇인가? — 응집도, 테스트성, 성능, 장애 격리, 확장성 중 우선순위
4. 허용 가능한 변경 범위는 어디까지인가? — 단일 파일, 도메인, 앱, 공통 패키지
5. 데이터 마이그레이션이나 배포 호환성이 필요한가?
6. 새 라이브러리 도입을 허용하는가? 허용 시 번들·라이선스·학습 비용 한계는?
7. 성공을 어떤 전후 지표나 시나리오로 판단할 것인가?
8. 이번에 명시적으로 하지 않을 것은 무엇인가?

### 목표의 좋은 형식

```markdown
## Goal

- 댓글 폴링, 낙관적 댓글 갱신, 좋아요 갱신을 독립적으로 검증할 수 있게 한다.
- 상세 모달 UI가 네트워크 재시도 규칙을 알지 않게 한다.

## Success Criteria

- 기존 Behavior Invariants가 모두 통과한다.
- 핵심 상태 전이 테스트가 추가된다.
- 상세 모달에서 직접 참조하는 비동기 상태 규칙이 감소한다.

## Out of Scope

- 댓글 전송 프로토콜을 WebSocket으로 바꾸지 않는다.
- 좋아요 API 스펙을 변경하지 않는다.
- 전체 프론트엔드의 데이터 패칭 방식을 일괄 교체하지 않는다.
```

### 산출물

- `docs/refactors/{name}/brief-fixed.md`

### 승인 게이트

```text
[GATE 2] 사용자가 Goal, Success Criteria, Behavior Invariants, Out of Scope을 확정할 때까지 대기
```

## 단계 3: 3안 비교와 기술 결정

### 목적

한 해결책에 성급히 고정되지 않고 비용·위험·효과가 다른 대안을 같은 기준으로 비교한다.

### 기본 대안 형태

항상 이름만 다른 세 안을 만들지 않는다. 보통 다음처럼 변화 강도가 다른 안을 포함한다.

1. **최소 개선안** — 현재 패턴을 유지하고 책임·순수 함수·테스트 이음새만 정리
2. **경계 재설계안** — 도메인 모듈이나 상태 소유권을 재정의하고 점진적으로 이동
3. **검증된 도구 도입안** — 라이브러리 또는 새로운 아키텍처 패턴으로 반복 책임을 위임

라이브러리가 문제에 맞지 않으면 3안도 자체 구현안으로 제시할 수 있다. “반드시 새 기술을 써야 한다”는 목표를 만들지 않는다.

### 고정 비교 기준

| #   | 기준               | 확인 내용                                           |
| --- | ------------------ | --------------------------------------------------- |
| 1   | 근본 원인 해결력   | 진단한 구조 원인을 실제로 줄이는가?                 |
| 2   | 동작 보존 난이도   | 기존 계약을 유지하고 검증하기 쉬운가?               |
| 3   | 책임·의존성        | 상태 소유권, 경계, 결합도가 어떻게 바뀌는가?        |
| 4   | 테스트 용이성      | 핵심 규칙을 독립적으로 검증할 수 있는가?            |
| 5   | 변경 범위          | 수정 파일·모듈·배포 단위는 얼마나 넓은가?           |
| 6   | 점진적 전환        | 중간 상태에서도 동작하고 작은 PR로 나눌 수 있는가?  |
| 7   | 롤백 가능성        | 실패 시 어느 지점에서 어떻게 되돌리는가?            |
| 8   | 성능·운영 영향     | 번들, 렌더, 쿼리, 메모리, 관측성이 어떻게 바뀌는가? |
| 9   | 기존 코드와 일관성 | 현재 컨벤션·ADR과 충돌하는가? 충돌할 가치가 있는가? |
| 10  | 유지 비용          | 학습, 업그레이드, 장기 소유 비용은 얼마인가?        |

### 라이브러리 도입 심사

라이브러리 도입안이 있으면 최신 공식 문서와 공식 저장소를 기준으로 다음을 확인한다.

- 해결하려는 책임과 라이브러리의 핵심 추상화가 일치하는가?
- 현재 Next.js, React, NestJS, Node.js 버전과 호환되는가?
- SSR/RSC/브라우저/서버 런타임 제약에 맞는가?
- 최근 릴리스와 유지보수 상태는 어떤가?
- 라이선스와 알려진 보안 이슈는 허용 가능한가?
- 번들 크기, 런타임 비용, 추가 의존성은 얼마인가?
- 테스트 대체 가능성과 vendor lock-in은 어떤가?
- 제거하거나 다른 구현으로 바꾸는 비용은 얼마인가?
- 현재 자체 구현에서 실제로 삭제되는 코드와 책임은 무엇인가?

“인기가 많다”, “요즘 많이 쓴다”는 도입 근거가 아니다.

#### Spike 규칙

핵심 호환성이나 성능이 문서만으로 불확실하면 제품 코드를 바로 마이그레이션하지 않는다. 폐기 가능한 작은 spike로 다음 하나만 검증한다.

- 한 사용자 흐름의 기술 호환성
- 한 상태 전이의 표현 가능성
- 한 API의 캐시·재시도 동작
- 번들 또는 응답 시간 영향

Spike 코드는 기본적으로 폐기하고 관찰 결과만 `plan.md`에 남긴다. 채택하려면 별도 승인한다.

### ADR 형식

```markdown
## Decision

### Context

어떤 구조 문제와 제약 때문에 결정이 필요한가?

### Decision

무엇을 선택하고 어느 범위에만 적용하는가?

### Alternatives

거부한 대안과 각각의 거부 이유는 무엇인가?

### Consequences

장점, 단점, 새로 생기는 위험과 운영 비용은 무엇인가?

### Migration

어떤 순서로 옮기며 중간 상태는 어떻게 동작하는가?

### Rollback

어떤 신호가 나오면 중단하고 어디까지 되돌리는가?
```

### 산출물

- 비교표와 ADR을 포함한 `docs/refactors/{name}/plan.md`

### 승인 게이트

```text
[GATE 3] 사용자가 세 대안 중 하나를 선택하고 ADR·마이그레이션·롤백을 확정할 때까지 대기
```

## 단계 4: 회귀 안전망 설계

### 목적

구조를 바꾸기 전에 현재 동작을 실행 가능한 테스트로 고정한다.

### 테스트 우선순위

1. **Characterization test** — 현재 코드가 실제로 하는 일을 고정
2. **Contract test** — API, DTO, 저장소, 외부 서비스 경계 고정
3. **State-transition test** — 낙관적 갱신, 롤백, 재시도, 큐 전이 고정
4. **Integration test** — 여러 모듈이 합쳐지는 핵심 흐름 고정
5. **E2E test** — 사용자에게 중요한 소수의 흐름 고정

모든 내부 구현을 스냅샷으로 얼리지 않는다. 테스트는 바꿀 구조가 아니라 보존할 동작을 검증해야 한다.

### 테스트가 어려운 경우

테스트를 쓰기 위해 최소한의 seam을 먼저 넣는 것은 허용한다.

- 시간, 네트워크, 저장소, 난수 같은 외부 효과 주입
- 큰 함수에서 순수 계산만 추출
- 전역 접근을 얇은 adapter 뒤로 이동

단, 이 단계에서 새 구조 전체를 미리 구현하지 않는다. “테스트 가능하게 만드는 최소 변경”만 별도 커밋으로 둔다.

### 회귀 행렬

| 시나리오      | 기존 결과           | 검증 수준 | 실패 시 조치        |
| ------------- | ------------------- | --------- | ------------------- |
| 정상 요청     | 응답·화면 상태      | 통합      | 구현 중단           |
| 네트워크 실패 | 롤백·메시지         | 상태 전이 | 구현 중단           |
| 중복 요청     | 중복 방지/멱등 결과 | 계약      | 설계 재검토         |
| 빈 값·경계값  | 현재 예외/기본값    | 단위      | 동작 변경 이슈 분리 |

### 산출물

- `docs/refactors/{name}/regression-plan.md`
- 구현 전에 추가할 테스트 목록

### 승인 게이트

```text
[GATE 4] 사용자가 회귀 시나리오와 현재 안전망 공백을 확인할 때까지 대기
```

## 단계 5: 동작 보존 체크포인트로 이슈 분해

### 목적

선택한 구조를 언제든 중단·검증·롤백할 수 있는 작은 작업으로 나눈다.

### 기능 기획과 다른 분해 원칙

Feature 이슈의 핵심은 “사용자에게 보이는 수직 슬라이스”다. Refactoring 이슈의 핵심은 다음 질문이다.

> 이 이슈만 머지해도 기존 동작이 유지되고 저장소가 정상 상태이며, 다음 이슈를 하지 않아도 되는가?

### 권장 순서

1. 특성화·계약 테스트 추가
2. 최소 seam 또는 새 경계 도입
3. 핵심 규칙을 새 경계로 한 조각 이동
4. 소비자를 하나씩 전환
5. 전환 결과와 운영 지표 확인
6. 이전 경로와 dead code 제거
7. 문서·ADR·전후 결과 갱신

이전 코드는 새 경로의 동등성이 확인되기 전에 삭제하지 않는다.

### 이슈 크기

- 반나절~하루 안에 구현과 검증이 가능한 크기
- 한 이슈에서 한 종류의 변화만 수행
- 대규모 rename, 라이브러리 도입, 상태 모델 변경을 한 번에 섞지 않음
- 각 이슈 종료 시 lint, type check, 관련 test, 필요 시 build가 통과

### 이슈 템플릿

```markdown
# 목적

이 체크포인트가 줄이는 구조적 위험은 무엇인가?

## Scope

- 수정할 경계와 파일

## Out of Scope

- 이번 이슈에서 하지 않을 일

## Behavior Invariants

- 반드시 유지할 외부 동작

## Acceptance Criteria

- [ ] Given [기존 조건], When [동일한 행동], Then [기존과 동일한 결과]
- [ ] Given [실패/경계 조건], When [행동], Then [정의된 롤백/예외 결과]
- [ ] 새 구조의 책임과 의존 방향이 plan.md의 결정과 일치한다.

## Verification

- [ ] 실행할 테스트·lint·type check·build 명령
- [ ] 필요한 수동 또는 운영 확인

## Rollback

- 되돌릴 커밋/flag/adapter와 데이터 호환 조건

## Dependency

- 선행 이슈와 후속 이슈
```

### 산출물

- `docs/refactors/{name}/issues.md`
- 승인 후 GitHub Issues

### 승인 게이트

```text
[GATE 5] 사용자가 각 이슈가 독립적으로 안전하고, 순서·검증·롤백이 구체적인지 확인할 때까지 대기
```

GitHub 이슈 생성과 프로젝트 보드 등록은 승인 이후에만 수행한다.

## 4. 구현 단계 운영 규칙

기획이 끝난 뒤 각 이슈를 구현할 때 다음을 강제한다.

### 변경 전

- 해당 이슈의 Behavior Invariants와 Out of Scope을 다시 읽는다.
- 작업 트리가 깨끗한지 또는 사용자 변경과 겹치는지 확인한다.
- 관련 테스트가 기준선과 동일하게 동작하는지 확인한다.

### 변경 중

- 기계적 이동/rename과 동작 변경을 분리한다.
- 한 번에 한 소비자 또는 한 규칙만 전환한다.
- 예상보다 변경 범위가 커지면 임의로 확장하지 말고 이슈를 다시 나눈다.
- 기존 실패를 리팩터링 성공으로 포장하지 않는다.
- 새 라이브러리의 추상화가 새는 경우 wrapper를 자동으로 추가하지 말고 경계 필요성을 다시 판단한다.

### 중단 조건

다음 중 하나가 발생하면 구현을 멈추고 plan.md를 재검토한다.

- Behavior Invariant를 유지할 수 없음
- 데이터 마이그레이션이나 공개 API 변경이 새로 필요함
- 예상하지 못한 도메인까지 변경 범위가 확장됨
- 성능·번들·쿼리 수가 합의한 허용 범위를 벗어남
- 라이브러리 호환성 또는 보안 전제가 틀림
- 롤백 경로가 사라짐

## 5. 완료 검증과 `result.md`

마지막 이슈가 끝나면 “코드가 컴파일된다”만 확인하지 않는다.

### 필수 비교

| 영역 | 확인 내용                                           |
| ---- | --------------------------------------------------- |
| 동작 | 모든 Behavior Invariants와 회귀 행렬 통과           |
| 구조 | 선택한 책임 경계와 의존 방향이 실제 코드에 반영됨   |
| 품질 | lint, type check, test, build 결과와 기존 실패 비교 |
| 성능 | 합의한 렌더·응답·쿼리·번들 기준 비교                |
| 운영 | 로그, 오류 처리, 배포·롤백 가능성 확인              |
| 문서 | ADR 상태, 다이어그램, 컨벤션 갱신                   |

Light 트랙(§2-1)은 이 표 전체를 정식으로 채우는 대신, 동작·품질 두 항목만 간단 요약으로 확인하고 나머지는 해당 없음으로 표시할 수 있다.

### `result.md` 형식

```markdown
# Result

## 변경 요약

무엇을 어떤 경계로 옮겼는가?

## Before / After

기준선과 완료 후 지표·구조·검증 결과 비교

## Behavior Verification

보존한 동작과 테스트 증거

## Decision Review

선택한 안의 장점과 실제로 드러난 비용

## Remaining Debt

의도적으로 남긴 문제와 다시 검토할 조건

## Follow-ups

별도 feature, bug-fix, 추가 리팩터링 후보
```

### 최종 게이트

```text
[GATE 6] 사용자가 전후 비교와 남은 부채를 확인한 뒤 리팩터링 사이클을 종료
```

## 6. VIBR 저장소에 적용할 때의 기본 규칙

VIBR은 `apps/web`, `apps/api`, `packages/dto`가 연결된 pnpm/Turborepo 모노레포다. 다음 규칙을 기본값으로 사용한다.

1. `packages/dto`의 계약 변경은 구조 변경으로 숨기지 않고 별도 검토한다.
2. 프론트엔드의 서버 상태, UI 상태, 플레이어 상태를 같은 종류로 취급하지 않는다.
3. React 훅이나 컴포넌트는 줄 수가 아니라 책임과 상태 전이 수를 기준으로 분리한다.
4. NestJS 서비스가 TypeORM 기본 Repository와 커스텀 Repository를 함께 쓸 때는 일관성 자체보다 트랜잭션·쿼리 조합·테스트 이음새를 먼저 진단한다.
5. Redis, Neo4j, MySQL을 오가는 변경은 장애 격리와 부분 실패 규칙을 baseline에 포함한다.
6. 기존 `CLAUDE.md`가 특정 라이브러리를 쓰지 않는다고 명시했다면 몰래 도입하지 않는다. 실제 문제와 비교 근거가 있을 때 새 ADR로 결정을 갱신한다.
7. 프론트엔드 테스트 안전망이 부족한 영역은 구조 이동보다 특성화 테스트 도입을 먼저 이슈로 둔다.

### 첫 진단 후보 예시

아래는 결론이 아니라 워크플로우를 시작할 수 있는 후보일 뿐이다.

- 게시글 반응 상태: 인증, 댓글 폴링, 낙관적 갱신, 롤백, 전역 상태 동기화의 책임 경계
- 플레이어: 큐 도메인 규칙, provider별 재생 제어, UI 상태의 소유권
- 게시글 백엔드: 도메인 서비스, 트랜잭션, TypeORM Repository와 커스텀 Repository의 경계
- 추천/트렌딩 파이프라인: stream consumer, 파싱, ranking, 저장소 장애의 격리
- 모달 컴포넌트: 화면 조합 책임과 서버 상태·도메인 규칙의 분리

후보를 동시에 고치지 않는다. 변경 빈도와 실제 문제 사례가 가장 분명한 하나부터 시작한다.

## 7. 승인 게이트 요약

| 게이트 | 확인 내용                                     |
| ------ | --------------------------------------------- |
| GATE 0 | 범위, Behavior Invariants, 현재 실패와 기준선 |
| GATE 1 | 근거가 가장 강한 문제 후보 하나 선택          |
| GATE 2 | Goal, Success Criteria, Out of Scope 확정     |
| GATE 3 | 3안 비교, ADR, 마이그레이션, 롤백 확정        |
| GATE 4 | 특성화·계약·통합 테스트 안전망 확정           |
| GATE 5 | 독립적으로 안전한 이슈와 실행 순서 확정       |
| GATE 6 | 전후 효과, 회귀 여부, 남은 부채 확인          |

Light 트랙(§2-1)은 GATE 1·GATE 2·GATE 3을 생략하고 GATE 0 → GATE 4 → GATE 5 → GATE 6만 거친다.

이 게이트들이 없으면 AI는 관찰하지 않은 문제를 해결하거나, 여러 구조 변경을 한 번에 수행하거나, 새 라이브러리 도입 자체를 성과로 오해하기 쉽다. 스킬에 각 게이트를 명시하고 사용자 승인 전에는 다음 단계로 진행하지 않는다.
