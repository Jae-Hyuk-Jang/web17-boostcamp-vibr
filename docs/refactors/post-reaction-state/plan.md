# Plan — post-reaction-state

## 3안

Stage 2(GATE 2)에서 이미 "라이브러리 도입 없음, 스토어 구조 유지"로 범위를 좁혔기 때문에, 워크플로우가 말하는 "③ 검증된 도구 도입안"은 여기서는 자체 구현안으로 대체합니다.

### 안 1 — 최소 개선안: 순수 함수로 로직만 공유

`PostCard.tsx`와 `usePostReactions.ts`의 `useState` 선언은 각자 그대로 두고, "스냅샷 → optimistic 계산 → store 반영 → API 호출 → 실패 시 롤백" 시퀀스만 순수 함수(`computeOptimisticLike`, `applyLikeOverride` 등)로 추출해 양쪽에서 호출한다.

### 안 2 — 경계 재설계안: 좋아요 전담 훅 추출 (권장)

`hooks/post/usePostLikeToggle.ts`를 새로 만들어 optimistic state(`useState`), submitting flag, API 호출, 롤백, `usePostReactionOverridesStore` 반영을 전부 캡슐화한다. `isAuthenticated`는 훅 내부에서 판단하지 않고 **호출부가 파라미터로 전달**한다(카드는 `useAuthStore`, `usePostReactions`는 기존처럼 자체 `authMe()` 결과를 그대로 전달 — 인증 소스 자체를 통일하지 않음, brief-fixed.md의 Out of Scope와 일치).

- `PostCard.tsx`: 기존 `handleToggleLike`/관련 `useState` 3개를 제거하고 `usePostLikeToggle` 호출로 교체.
- `usePostReactions.ts`: 좋아요 관련 `useState`(`isLiked`, `likeCount`, `isSubmittingLike`)와 `toggleLike`를 제거하고, 내부에서 `usePostLikeToggle`을 호출해 그 결과를 기존 `Result` 타입의 동일한 필드명으로 그대로 반환한다(훅 합성 — `PostCardDetailModal.tsx`는 변경 없음).

### 안 3 — 더 넓은 재설계안: 스토어를 유일한 진실 공급원으로(로컬 state 완전 제거)

로컬 `useState` 자체를 없애고, 카드/모달 모두 `usePostReactionOverridesStore`를 직접 구독해서 읽고, 토글도 스토어 액션이 API 호출까지 포함하도록 승격한다.

## 선택: 안 2 (전담 훅 추출)

안 1은 "지금 당장은 더 안전"하지만 Stage 2에서 확정한 응집도·확장성 목표를 실제로 달성하지 못합니다(소유권 중복이 남음 — 다음에 반응 타입을 추가해도 또 두 곳을 고쳐야 함). 안 3은 근본 해결력은 가장 높지만, Stage 2에서 이미 "스토어 구조 유지"로 범위를 좁혔고, `apps/web`의 기존 아키텍처 관례(zustand는 동기화 전용)와 정면으로 부딪히며, 변경 범위·롤백 난이도가 이번 사이클에 비해 과도합니다.

## ADR

### Context

좋아요 토글의 낙관적 갱신·롤백·스토어 동기화 로직이 `PostCard.tsx`와 `usePostReactions.ts`에 독립적으로 중복 구현되어 있다(Stage 1 diagnosis.md 후보 ①). 새 반응 타입을 추가하려면 이 패턴을 또 한 번 복제해야 하는 구조다.

### Decision

`hooks/post/usePostLikeToggle.ts`를 신설해 좋아요의 optimistic state·submitting flag·API 호출·롤백·store 반영을 캡슐화한다. `isAuthenticated`는 훅 파라미터로 주입받아, 카드/모달이 기존에 쓰던 인증 판단 소스를 그대로 유지한다. `usePostReactions.ts`는 이 훅을 내부에서 호출해 기존 `Result` 타입과 동일한 형태로 반환하는 방식(훅 합성)으로 좋아요 부분을 위임하고, 댓글 관련 로직은 그대로 둔다.

### Alternatives

- **안 1(순수 함수 공유)**: 기각. 상태 소유권 중복(각자 `useState`)이 그대로 남아 Stage 2의 확장성 목표(새 반응 타입 추가 시 파일 수 감소)를 달성하지 못함.
- **안 3(스토어 승격)**: 기각. 근본 해결력은 가장 높지만 (a) Stage 2에서 스토어 구조 유지로 범위를 이미 확정했고, (b) zustand를 동기화 전용으로 쓰는 기존 관례와 충돌하며, (c) 변경 범위·롤백 난이도가 이번 Full 트랙 사이클에 비해 과도함 — 별도 사이클(스토어 자체 재설계)로 논의할 가치는 있으나 이번엔 아님.

### Consequences

- **장점**: 좋아요 로직의 단일 진실 소스 확보, 다음 반응 타입 추가 시 훅 패턴 복제만으로 확장 가능, 기존 특성화 테스트(#36)로 안전하게 검증 가능.
- **단점**: `isAuthenticated`를 파라미터로 주입받는 설계라 인증 소스 불일치(카드 vs 모달)는 이번에 해소되지 않고 그대로 남는다(Out of Scope, 의도된 결정). `usePostReactions.ts`가 내부적으로 두 훅을 합성하는 구조가 되어 파일을 처음 보는 사람은 "위임"이라는 한 단계를 더 따라가야 한다.
- **새로 생기는 위험**: 훅 합성 과정에서 `usePostReactions`의 기존 반환 필드명·타입을 정확히 유지하지 못하면 `PostCardDetailModal.tsx`가 깨질 수 있음 — 이슈 분해 시 "반환 타입 동일성 확인"을 명시적 Acceptance Criteria로 둔다.

### Migration

1. `usePostLikeToggle.ts` 작성(특성화 테스트가 이미 검증한 동작을 그대로 이관).
2. `PostCard.tsx`를 이 훅으로 전환, 기존 `PostCard.test.tsx` 통과 확인.
3. `usePostReactions.ts`가 내부에서 이 훅을 호출하도록 전환(댓글 로직은 그대로), 기존 `usePostReactions.test.ts` 통과 확인.
4. 두 전환 사이에도 앱은 항상 정상 동작하는 중간 상태를 유지한다(한쪽만 전환해도 다른 쪽은 기존 구현 그대로 동작).

### Rollback

각 전환 단계는 독립 커밋 — 문제가 생기면 해당 커밋만 되돌리면 이전 동작으로 복귀한다. `usePostLikeToggle.ts` 자체를 되돌려도 아직 그걸 쓰지 않는 소비처는 영향받지 않는다.
