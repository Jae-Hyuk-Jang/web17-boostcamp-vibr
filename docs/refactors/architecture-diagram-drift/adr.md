# ADR — architecture-diagram-drift

## 3안 비교

### 안 1 — 최소 개선안

PRD에서 확인된 6개 stale/부분 stale 다이어그램(백엔드 모듈, 프론트엔드 최상위 폴더, 컴포넌트 cross-import, 인증 세션 상태 흐름도, zustand 스토어 사용 현황, usePostReactionOverridesStore 상세 흐름 + 서버 상태 캐싱의 죽은 참조)만 실제 코드에 맞게 정밀 수정한다. 파일 구조(단일 HTML, 섹션 순서, 상단 배너 형식)는 그대로 유지한다.

### 안 2 — 섹션별 신선도 표시 추가

안 1의 수정에 더해, 각 `<h2>` 섹션에 "마지막 검증일" 개별 타임스탬프를 추가한다. 지금은 문서 전체가 상단 배너 하나로 신선도를 주장하는데, PRD가 지목한 근본 원인(사이클 종료 시 이 문서를 갱신 대상에 포함시키는 트리거가 없음)을 부분적으로 완화한다 — 최소한 "이 섹션은 언제 마지막으로 검증됐는지"가 개별적으로 드러나면, 다음에 이 문서를 참고하는 사람이 오래된 섹션을 더 쉽게 의심할 수 있다.

### 안 3 — 의존성 그래프 자동화 도구 도입

"구조 스캔" 계열 다이어그램(백엔드 모듈, 프론트엔드 최상위 폴더, 컴포넌트 cross-import — 총 3개)을 `madge`나 `dependency-cruiser` 같은 도구로 스크립트 자동 생성하고, 해석이 필요한 "상태 흐름" 계열 다이어그램(인증 세션, 음악 재생, zustand 스토어 현황, usePostReactionOverridesStore, 서버 상태 캐싱 — 총 5개)은 수동 유지한다.

## 라이브러리 도입 심사 (안 3)

- **해결 책임-핵심 추상화 일치**: `madge`/`dependency-cruiser`는 "파일 간 import 그래프"를 뽑는 도구라, 구조 스캔 3개 다이어그램(모듈 import, 폴더 import, 컴포넌트 cross-import)과는 책임이 정확히 일치한다. 다만 이번 PRD가 다루는 6개 stale 다이어그램 중 3개(인증 세션, zustand 스토어 현황, usePostReactionOverridesStore)는 "누가 이 상태를 읽고 쓰는가"라는 의미론적 해석이 필요해 이 도구들의 추상화(정적 import 그래프)로는 커버되지 않는다.
- **버전 호환성/런타임 제약**: 두 도구 모두 Node CLI라 이 모노레포(pnpm/Turborepo)에 devDependency로 추가하는 데 기술적 장벽은 없다.
- **최근 릴리스·유지보수 상태**: 둘 다 활발히 유지되는 편(별도 spike로 확인 필요, 이번 사이클에서는 수행하지 않음).
- **제거 비용**: 낮음(devDependency 제거 + 생성 스크립트 삭제).
- **실제로 삭제되는 기존 코드/책임**: 없음 — mermaid 텍스트를 수동으로 쓰던 걸 스크립트 출력으로 바꾸는 것뿐, 삭제될 기존 로직이 없다.
- **결론**: 추상화 일치는 되지만 이번 PRD가 다루는 문제의 상당 부분(상태 흐름 해석형 다이어그램)을 해결하지 못하고, CLAUDE.md 원칙("실제 문제와 비교 근거가 쌓였을 때"만 새 라이브러리 도입)에 따라 지금은 도입 근거가 부족하다.

## 의사결정 인터뷰 로그

**Q. 이번 architecture-diagram-drift 사이클을 어떻게 진행할까요? PRD에서 확인된 6개 stale 다이어그램을 고치는 건 공통이지만, '왜 매번 누적되는가'(근본 원인: 사이클별 갱신 트리거 부재)까지 이번에 같이 손볼지가 갈립니다.**
A. 안 1 — 최소 개선안. (추천안 그대로 채택 — 사용자가 추천안을 그대로 승인)

## 선택: 안 1

**안 1(최소 개선안)**을 선택한다. 근거:

- PRD의 Success Criteria가 이미 "6개 다이어그램을 현재 코드와 일치시킨다"로 명확히 정의돼 있고, 재발 방지 메커니즘(안 2의 섹션별 타임스탬프, 안 3의 자동화)은 PRD의 Out of Scope/Follow-up에서 "별도 작업"으로 이미 분리해 뒀다.
- 안 2는 비용이 낮아 매력적이지만, "섹션별 타임스탬프를 계속 갱신하는 습관"이라는 새로운 운영 부담을 이 문서에만 도입하는 것이라 — 실제로 지켜질지는 다음 사이클들이 증명해야 하는 가설이다(Hypothesis). 이번엔 지키지 않는다.
- 안 3은 구조 스캔 3개엔 잘 맞지만 이번 PRD가 다루는 6개 중 절반(상태 흐름 3개)을 해결하지 못해 "같은 문제를 두 가지 방식(자동+수동)으로 유지"하게 되는 비일관성이 생긴다. 라이브러리 도입 심사 결론과도 일치.

## ADR 본문

### Context

`docs/architecture/index.html`의 9개 다이어그램 중 6개가 실제 코드와 어긋나 있다(PRD 참고). 근본 원인은 "저장소 전역 스냅샷 문서를 어느 리팩터링 사이클이 갱신 책임을 지는가"에 대한 트리거 부재이지만, 이번 사이클은 그 구조적 원인 자체를 고치기보다 "지금 시점의 정확성을 되찾는 것"을 목표로 한다(사용자 결정).

### Decision

6개 다이어그램(백엔드 모듈, 프론트엔드 최상위 폴더, 컴포넌트 cross-import, 인증 세션 상태 흐름도, zustand 스토어 사용 현황, usePostReactionOverridesStore 상세 흐름)과 서버 상태 캐싱 다이어그램의 `AuthBootstrap` 참조를 실제 코드 기준으로 정밀 수정한다. 이미 정확한 3개(ERD, 음악 재생 상태 흐름도, 살아있는 3개 스토어 노드)는 건드리지 않는다. 상단 "마지막 갱신" 배너를 오늘 날짜와 이번에 반영한 사이클 목록으로 갱신한다.

### Alternatives

- 안 2(섹션별 신선도 표시)는 기각 — 근본 원인 완화 효과가 제한적이고 새 운영 관습을 이 문서에만 도입하는 비일관성이 있어, 사용자가 "최소 개선안"을 명시적으로 선택함.
- 안 3(자동화 도구 도입)은 기각 — 문제의 절반(상태 해석형 다이어그램)을 해결하지 못하고, CLAUDE.md의 라이브러리 도입 원칙(비교 근거 필요)을 이번 PRD 단독으로 충족하지 못함.

### Consequences

- **장점**: 지금 시점 기준으로 문서가 정확해진다. 애플리케이션 코드 변경이 전혀 없어 위험이 사실상 0에 가깝다.
- **단점**: 근본 원인(갱신 트리거 부재)이 그대로 남아, 다음 리팩터링 사이클이 또 이 문서를 빠뜨리면 동일한 drift가 재발할 수 있다(PRD의 Follow-up에 이미 기록됨).
- **새로 생기는 위험**: 없음(문서 전용).
- **운영 비용**: 없음 — 이번 수정 이후 별도로 유지해야 할 새 규칙이 생기지 않는다(안 2/3과 달리).

### Migration

Behavior Invariant("과거 사이클 서술은 과거형으로 보존")를 지키면서, 아래 두 체크포인트 순서로 진행한다. 각 체크포인트는 파일 하나의 다른 섹션들이라 서로 독립적이며, 어느 순서로 해도 무방하지만 "구조 스캔형"과 "상태 관리형"으로 종류를 나눠 한 이슈에서 한 종류만 바꾼다.

1. **체크포인트 1**: 구조 스캔형 3개 다이어그램(백엔드 모듈, 프론트엔드 최상위 폴더, 컴포넌트 cross-import)에 누락된 노드/엣지 추가.
2. **체크포인트 2**: 상태 관리형 4개 다이어그램(인증 세션 재작성, zustand 스토어 현황에서 죽은 5개 제거, usePostReactionOverridesStore를 쿼리 캐시 기반 다이어그램으로 교체, 서버 상태 캐싱의 `AuthBootstrap` 참조 수정) + 상단 배너 갱신 + 파일 전체 최종 grep 검수.

중간 상태(체크포인트 1만 머지된 상태)에서도 문서는 "이전보다 더 정확해진 상태"이며 깨진 링크나 렌더링 오류가 없다 — 정적 HTML이라 부분 갱신이 페이지를 깨뜨리지 않는다.

### Rollback

문서 전용 변경이라 롤백 위험이 사실상 없다. 만약 재작성한 다이어그램이 실제 코드와 다르다는 게 사후에 발견되면(예: grep 대조를 잘못함), 해당 체크포인트 커밋만 `git revert`하면 이전 상태(더 오래됐지만 이전에 검증된 상태)로 즉시 되돌아간다.

## 회귀 안전망

### 테스트 우선순위

문서 전용 변경이라 자동화된 테스트 스위트에 추가할 항목은 없다(app 코드 미변경, `pnpm test`는 기준선과 동일하게 유지되는 것만 확인). 대신 PRD 작성 시 사용한 "grep 기반 전수 대조"를 각 체크포인트의 회귀 검증 수단으로 삼는다.
