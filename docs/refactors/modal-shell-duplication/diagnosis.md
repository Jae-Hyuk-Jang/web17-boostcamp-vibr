# Diagnosis — modal-shell-duplication

## 진단 원칙 적용

- baseline.md에서 이미 "변경 빈도가 높다"는 근거는 기각했다 — 실제 문제는 **8개 파일에 흩어진 backdrop·닫기·z-index·접근성 로직의 중복과 불일치**다.
- 아래 모든 판단에 Fact(코드로 직접 확인) / Inference(여러 사실에서 도출한 해석) / Hypothesis(아직 검증하지 않은 가설) 등급을 표시한다.

## 증상 → 원인 체인

```
증상: 모달을 새로 추가하거나 닫기 동작을 손보려면 참고할 공통 지점이 없어
      매번 새로 판단해야 하고, 그 결과 8개 파일이 서로 다른 방식으로 갈라졌다.
  ↓ 왜?
직접 원인: backdrop 렌더링, 배경 클릭 판정(4가지 다른 구현), z-index 값,
           접근성 속성(role/aria-modal)이 각 모달 컴포넌트 본문에 개별 하드코딩돼 있다.
  ↓ 왜?
구조 원인: "모달의 공통 뼈대(shell)"를 표현하는 별도 경계(컴포넌트 또는 훅)가 없다 —
           `useSwipeToDismiss`, `usePostDetailUxLog`처럼 이미 성공적으로 뽑아낸
           선례가 있는 반면, 모달 shell은 그런 경계 없이 매번 복붙·재구현되어 왔다.
```

## 후보

### 후보 A — 공통 Modal Shell 추출 (권장)

backdrop 렌더링, 배경 클릭 판정(하나의 방식으로 통일하되 "닫기 비활성" 옵션 유지), z-index(공유 상수/토큰), 접근성 속성(`role="dialog"`, `aria-modal`)을 하나의 공통 컴포넌트(또는 훅)로 묶어 8개 모달이 이를 소비하도록 전환한다.

| 기준          | 점수 | 근거                                                                                                         |
| ------------- | ---- | ------------------------------------------------------------------------------------------------------------ |
| 변경 빈도     | 2    | 이력 자체는 낮지만, 모달이 8개나 이미 있고 계속 늘어난 걸 보면 앞으로도 추가될 가능성이 있음(Inference)      |
| 결함 위험     | 4    | z-index 겹침 가능성(Inference로 뒷받침된 실제 버그 후보) + 접근성 편차 + 배경클릭 4가지 불일치가 동시에 걸림 |
| 영향 범위     | 4    | 8개 파일 전부 건드림 — 이번 사이클 중 가장 넓음                                                              |
| 근거 강도     | 5    | 거의 전부 Fact, z-index 문제만 Inference(스태킹 컨텍스트 분석으로 뒷받침)                                    |
| 안전망 가능성 | 3    | 지금 테스트 0개라 특성화 테스트부터 필요하지만, RTL로 backdrop 클릭/닫기 버튼/접근성 속성은 충분히 검증 가능 |
| 구현 비용     | 4    | 8개 파일을 전부 새 shell로 옮겨야 해서 중간~큼                                                               |

**YAGNI**: "그렇다" — 이미 8개 모달이 있고, 이번 세션에서도 새 모달(#41 사이클과 무관하게)이 계속 추가돼 왔다(git 이력상 최근에도 늘어남). 다음 모달을 또 추가할 때 지금처럼 각자 판단하게 두면 불일치가 더 쌓인다.

### 후보 B — z-index만 공유 상수로 토큰화

`constants/`에 모달 z-index 상수(예: `MODAL_Z_INDEX`)를 하나 두고 8개 모달이 이를 참조하게만 바꾼다. backdrop 클릭 판정·접근성 속성은 손대지 않는다.

| 기준          | 점수 | 근거                                                                               |
| ------------- | ---- | ---------------------------------------------------------------------------------- |
| 변경 빈도     | 1    | -                                                                                  |
| 결함 위험     | 4    | 가장 시급해 보이는 문제(모바일 하단 네비게이션에 모달이 가려질 가능성)를 직접 해결 |
| 영향 범위     | 2    | 8개 파일이지만 클래스 값 하나만 바뀜 — 국지적                                      |
| 근거 강도     | 4    | 값이 다르다는 건 Fact, 실제 겹침은 아직 Inference                                  |
| 안전망 가능성 | 2    | 시각적 겹침은 자동화 테스트로 검증하기 어려워 브라우저 확인이 필요함               |
| 구현 비용     | 1    | 매우 작음                                                                          |

**YAGNI**: "그렇다, 최소한으로는" — 결함 위험 대비 구현 비용이 가장 낮아 후보 A를 하지 않더라도 이것만은 할 가치가 있다.

### 후보 C — 닫기 버튼 마크업만 공통 컴포넌트화

`<X>` 아이콘 + 버튼 스타일을 `ModalCloseButton` 같은 작은 컴포넌트로 뽑는다.

| 기준          | 점수 | 근거                                      |
| ------------- | ---- | ----------------------------------------- |
| 변경 빈도     | 1    | -                                         |
| 결함 위험     | 1    | 마크업 반복이지 실제 결함은 아님          |
| 영향 범위     | 2    | 7개 파일, 각 파일에서 버튼 하나만 교체    |
| 근거 강도     | 3    | Fact지만 결함 위험이 낮아 우선순위는 낮음 |
| 안전망 가능성 | 4    | 작은 컴포넌트라 테스트 쉬움               |
| 구현 비용     | 1    | 매우 작음                                 |

**YAGNI**: "아니오"에 가까움 — 그 자체로는 급하지 않다. 후보 A를 선택하면 자연히 포함되는 하위 작업으로 보는 게 맞다.

### 후보 D — layout의 다른 오버레이까지 전부 통합(범위 밖)

`MobileBottomSheet.tsx`, `MobileNotiOverlay.tsx`, `MobileNowPlaylistModal` 등 `MODAL_TYPES` 밖에 있는 유사 오버레이 패턴까지 이번에 함께 통합하는 안.

독립 후보로 두지 않는다 — 이 오버레이들이 정말 "모달 shell"과 같은 패턴인지조차 baseline.md에서 판별을 미뤄둔 상태라 근거가 약하고(brief-original.md 제약), 지금 범위를 넓히면 8개 모달이라는 이미 명확한 대상에서 벗어나 YAGNI 위반이 된다. 후보 A가 자리 잡은 뒤 별도 사이클로 재평가할 것을 권장한다.

## 권장 후보

**후보 A(공통 Modal Shell 추출)를 권장합니다.** 근거 강도가 가장 높고, 결함 위험(z-index 겹침 가능성)·영향 범위가 모두 커서 이번 사이클에서 다룰 가치가 분명합니다. 다만 구현 비용이 후보 중 가장 크므로, 범위를 줄이고 싶으시면 **후보 B(z-index만)**를 먼저 좁게 처리하고 나머지는 다음 사이클로 미루는 것도 합리적인 선택입니다.

AI의 추천과 사용자의 최종 선택은 다를 수 있습니다. 다른 후보를 선택하시면 그 근거를 이 문서에 추가하겠습니다. 최종 선택권은 항상 사용자에게 있습니다.
