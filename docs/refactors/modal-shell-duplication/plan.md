# Plan — modal-shell-duplication

## 3안

brief-fixed.md에서 라이브러리 도입 없음(자체 구현)을 이미 확정했으므로, 워크플로우의 "③ 검증된 도구 도입안"은 "로직만 훅으로 감싸는 자체 구현 대안"으로 대체한다. 세 안 모두 자체 구현이며, 차이는 "얼마나 캡슐화할 것인가"다.

### 안 1 — 최소 개선안: 각 파일 개별 패치

z-index를 상수 하나로 옮기고, 8개 파일 각각에 `role="dialog"`/`aria-modal` 속성만 개별로 추가한다. backdrop 렌더링과 배경 클릭 판정 로직(4가지 다른 방식)은 각 파일에 그대로 둔다.

### 안 2 — 경계 재설계안: 공통 `ModalShell` 컴포넌트로 감싸기 (권장)

`ModalShell` 컴포넌트를 신설해 backdrop `div` 렌더링, 배경 클릭 판정(`closeOnBackdrop` prop), z-index, `role`/`aria-modal` 속성을 전부 캡슐화한다. 8개 모달은 자신의 패널 JSX를 `<ModalShell onClose={...} closeOnBackdrop={...}>{패널}</ModalShell>` 형태로 감싸도록 전환한다.

### 안 3 — Headless 훅으로 로직만 제공

`useModalShell({ onClose, closeOnBackdrop })` 훅이 배경 클릭 판정 핸들러, z-index 값, 접근성 속성 객체(`{ role: 'dialog', 'aria-modal': true }`)를 반환한다. backdrop `div`와 패널 JSX 자체는 각 모달이 그대로 작성하되, 훅이 반환한 값을 스프레드해서 쓴다.

## 선택: 안 2 (ModalShell 컴포넌트)

이 저장소는 실제로 훅 추출 선례가 압도적으로 많아(기준 9), 안 3이 "기존 코드와의 일관성"에서는 더 높은 점수를 받는다. 하지만 diagnosis.md가 지적한 문제 중 **닫기 버튼 마크업 반복**과 **backdrop `div`의 반복된 `className`/구조**는 "로직"이 아니라 "반복되는 DOM 구조" 자체가 문제이고, brief-fixed.md의 Success Criteria 1("이 4가지 로직이 각 모달 파일에 직접 구현되어 있지 않다")을 안 3만으로는 충족하지 못한다(마크업이 여전히 8곳에 남기 때문). 상태·로직을 캡슐화하는 데는 훅이 맞지만, **공유되는 DOM 구조를 캡슐화하는 데는 컴포넌트가 정석**이라 안 2를 선택한다. 안 1은 Success Criteria 1을 아예 충족하지 못해 제외한다.

## ADR

### Context

8개 모달 컴포넌트가 backdrop 렌더링, 배경 클릭 판정(4가지 다른 방식), z-index(6가지 값), 접근성 속성(`role`/`aria-modal`, 8개 중 1개만 보유)을 각자 손으로 구현하고 있다. 특히 z-index 문제는 `MobileBottomNav`(`z-[10000]`, 모달 열림 여부와 무관하게 항상 렌더링)보다 낮은 값을 쓰는 5개 모달이 모바일에서 하단 네비게이션에 가려질 수 있는 결함 위험으로 이어진다(diagnosis.md, Inference).

### Decision

`apps/web/src/components/modals/ModalShell/ModalShell.tsx`를 신설해 backdrop `div`(z-index 상수 포함), 배경 클릭 판정(`closeOnBackdrop` prop, 기본값 `true`), `role="dialog"`/`aria-modal="true"`를 캡슐화한다. z-index 상수는 `apps/web/src/constants/modal.ts`(신설)에 `MODAL_Z_INDEX`로 둔다. 8개 모달은 각자의 패널 JSX를 `ModalShell`로 감싸는 형태로 전환한다. 닫기 버튼(X 아이콘) 마크업은 `ModalShell`과 별도로 작은 `ModalCloseButton` 컴포넌트로 뽑아, `ModalShell`이 강제하지 않고 각 모달이 선택적으로 쓰게 한다(일부 모달은 닫기 버튼 위치·스타일이 패널 헤더 안에 있어 Shell이 직접 렌더링하기 어려움).

### Alternatives

- **안 1(개별 패치)**: 기각. Success Criteria 1(중복 제거)을 충족하지 못하고, 지금과 같은 불일치가 다음 모달에서도 반복될 것이다.
- **안 3(Headless 훅)**: 기각하되 완전히 버리지 않는다. `ModalShell` 컴포넌트 **내부 구현**에서 배경 클릭 판정 로직을 별도 함수/훅으로 뽑아 테스트 이음새를 확보하는 것은 유효한 구현 세부사항이다(사용자가 선택하는 "대안"이 아니라 "구현 방식"). 이 프로젝트의 훅 선호 컨벤션은 존중하되, 이번 문제(공유되는 DOM 구조)에는 컴포넌트 경계가 더 적합하다.

### Consequences

- **장점**: 8개 모달의 backdrop·닫기 판정·z-index·접근성이 한 곳에 응집되어, 다음 모달 추가 시 `ModalShell`만 쓰면 이 4가지를 다시 판단하지 않아도 된다. z-index를 상수 하나로 관리하게 되어 diagnosis.md의 결함 위험이 구조적으로 해소된다.
- **단점**: 이 프로젝트의 지배적 패턴(훅 추출)과 다른 결을 갖는 컴포넌트 경계가 하나 생긴다 — 다음에 유사한 "공유 DOM 구조" 문제가 생기면 이 선례를 참고하되, "로직 공유는 훅, 구조 공유는 컴포넌트"라는 구분 기준을 팀 컨벤션으로 남겨둘 필요가 있다(백로그 #42와 연결 지점).
- **새로 생기는 위험**: 8개 모달의 패널 레이아웃이 제각각이라(`max-w-lg`, `max-w-md`, `max-w-2xl`, `max-w-5xl` 등), `ModalShell`이 강제하는 wrapper 구조(`flex items-center justify-center`)가 특정 모달의 레이아웃과 충돌하지 않는지 모달별로 확인이 필요하다 — 이슈 분해(Stage 5)에서 모달 하나씩 전환하며 각각 검증한다.

### Migration

1. `apps/web/src/constants/modal.ts` 신설 — `MODAL_Z_INDEX` 상수 정의(현재 값 중 가장 안전한 상한선 검토, `MobileBottomNav`의 `z-[10000]`보다 높게).
2. `apps/web/src/components/modals/ModalShell/ModalShell.tsx` 신설 — backdrop 렌더링, `closeOnBackdrop` 판정, 접근성 속성 캡슐화. 특성화 테스트 이전에 8개 모달 중 어느 것도 아직 이 컴포넌트를 쓰지 않는 안전한 상태로 둔다.
3. `ModalCloseButton` 컴포넌트 신설(선택적 소비).
4. 8개 모달을 하나씩 `ModalShell`로 전환 — 순서는 이슈 분해 단계에서 위험도(레이아웃 충돌 가능성)가 낮은 것부터 정한다.
5. 전환 완료 후 각 모달의 인라인 backdrop/판정/z-index/접근성 코드를 제거한다.

### Rollback

`ModalShell`/`ModalCloseButton`은 신규 파일이라 아직 아무도 쓰지 않는 단계에서는 파일 삭제만으로 충분하다. 각 모달의 전환은 파일 단위 커밋으로 나눠, 특정 모달에서 레이아웃 충돌이 발견되면 그 모달의 전환 커밋만 되돌리고 나머지는 유지할 수 있다.
