# Diagnosis — post-detail-modal-responsibility

## 진단 원칙 적용

- baseline.md에서 이미 "변경 빈도가 높다"는 근거는 기각했다 — 이 파일의 실제 문제는 **책임 응집도**(한 파일 안에 무관한 관심사가 몇 개나 섞여 있는가)다.
- 아래 모든 판단에 Fact(코드로 직접 확인) / Inference(해석) / Hypothesis(미검증) 등급을 표시한다.

## 탐색 항목 체크 (baseline.md 근거 기반)

| 항목          | 관찰                                                                                                                                                                                                                                                                             | 등급      |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------- |
| 책임 응집도   | 한 컴포넌트가 모달 상태·반응 상태·본문수정·UX 로그·라우팅 전환·좋아요유저목록·재생트리거·스와이프 8가지를 함께 수행                                                                                                                                                              | Fact      |
| 결합도        | UX 로그 수집(`playedMusicIdsRef` 등)이 재생 트리거(`handlePlayFromPost`) 콜백 안에 직접 섞여 있어, 재생 로직을 건드리면 로그 로직까지 같이 읽어야 함                                                                                                                             | Fact      |
| 상태 소유권   | 본문 수정 상태(`isEditing` 등)와 UX 로그 상태(ref 5개)가 전부 이 컴포넌트에 로컬로만 존재 — 다른 곳에서 재사용 불가                                                                                                                                                              | Fact      |
| 경계 명확성   | UI 조합(모달 열림/레이아웃)과 도메인 무관 관심사(로깅, 라우팅)가 구분 없이 한 함수 본문에 순서대로 나열됨                                                                                                                                                                        | Fact      |
| 테스트 이음새 | 테스트 0개(baseline.md). UX 로그의 `Date.now()`/`setInterval` 외부효과가 그대로 컴포넌트 안에 있어 seam이 없음                                                                                                                                                                   | Fact      |
| 오류·동시성   | UX 로그의 `emitOnce` 가드가 "닫기 버튼 클릭"과 "unmount cleanup" 두 경로 모두에서 안전하게 동작해야 하는데, 그 보장이 `emittedRef`라는 단일 ref에 의존 — 로직 자체는 Fact로 확인했지만 "두 경로가 정말 안전하게 겹치지 않는지"는 특성화 테스트 없이는 확신하기 어려움(Inference) | Inference |
| 데이터 계약   | `Post` DTO와 화면 로컬 상태(`editedContent` 등) 경계는 비교적 명확 — 이 부분은 문제로 안 봄                                                                                                                                                                                      | Fact      |
| 운영성        | UX 로그가 유일한 "운영 지표 생성 지점"인데 그 로직이 컴포넌트에 묻혀 있어 재사용/독립 검증이 안 됨                                                                                                                                                                               | Fact      |
| 변경 이력     | baseline.md에서 이미 기각(기능적 변경 커밋 0건)                                                                                                                                                                                                                                  | Fact      |
| 죽은 추상화   | 없음 — 오히려 `useSwipeToDismiss`처럼 이미 잘 추출된 훅도 있음(반례로 참고 가치 있음: "추출하면 이렇게 깔끔해진다"는 실제 사례)                                                                                                                                                  | Fact      |

## 증상 → 원인 체인

```
증상: PostCardDetailModal.tsx를 수정하려면 8가지 무관한 관심사를 동시에 이해해야 한다.
  ↓ 왜?
직접 원인: UX 로그 수집(105줄, ref 5개+effect 2개+callback 2개)과 재생 트리거가
           컨테이너 컴포넌트 본문에 인라인으로 구현되어 있고, 다른 관심사와 순서상 나열만 되어 있다.
  ↓ 왜?
구조 원인: "화면을 조합하는 책임"과 "도메인 무관 부가 기능(로깅)"을 분리하는 경계(훅)가
           없다 — useSwipeToDismiss는 이미 이 경계를 갖고 있지만 UX 로그는 그렇지 않다.
```

## 후보

### 후보 A — UX 로그 수집을 전담 훅으로 추출 (권장)

`openedAtRef`/`playedMusicIdsRef`/`listenMsByMusicRef`/`lastTickRef`/`emittedRef` 5개 ref, 모달 열림 초기화 effect, 1초 tick effect, `emitPostDetailSummary`/`emitOnce` 콜백을 `usePostDetailUxLog` 같은 훅으로 추출. 재생 트리거(`handlePlayFromPost`)의 "재생한 곡 id 기록" 부분도 이 훅이 제공하는 콜백으로 위임.

| 기준          | 점수 | 근거                                                                                                            |
| ------------- | ---- | --------------------------------------------------------------------------------------------------------------- |
| 변경 빈도     | 3    | 이력은 없지만 가장 복잡한 블록이라 향후 버그 발생 시 우선 손댈 가능성이 높음(Inference)                         |
| 결함 위험     | 3    | 중복 전송 방지 가드가 "닫기"와 "unmount" 두 경로에 걸쳐 있어 실수 여지가 있음                                   |
| 영향 범위     | 2    | 파일 1개, 국지적                                                                                                |
| 근거 강도     | 5    | 전부 Fact — 코드로 직접 확인된 가장 큰 단일 응집도 문제                                                         |
| 안전망 가능성 | 3    | 순수 계산(dwell/누적) 부분은 추출 후 유닛테스트 가능, `Date.now`/`setInterval`은 주입 가능한 seam으로 분리 필요 |
| 구현 비용     | 3    | 중간 — ref 5개·effect 2개·callback 2개 이동                                                                     |

**YAGNI**: "그렇다" — 이 로직이 이미 가장 복잡하고, 다른 상세 화면(예: 향후 트랙 상세 페이지 등)에도 비슷한 체류시간 로깅이 필요해질 가능성이 있다(Hypothesis, 확정 아님). 지금 정리해두면 재사용 여지가 생긴다.

### 후보 B — 반응형 라우팅 전환을 전담 훅으로 추출

데스크톱→모바일 리사이즈 감지 + 프로필 페이지 라우팅 전환(78-99행, 22줄)을 별도 훅으로 추출.

| 기준          | 점수 | 근거                                             |
| ------------- | ---- | ------------------------------------------------ |
| 변경 빈도     | 1    | 변경 이력 없음, 향후 변경 가능성도 낮아 보임     |
| 결함 위험     | 2    | 로직이 짧고 단순 — 실수 여지 적음                |
| 영향 범위     | 1    | 22줄, 이미 국지적으로 응집됨                     |
| 근거 강도     | 3    | Fact지만 "문제"로 보기엔 이미 충분히 짧고 명확함 |
| 안전망 가능성 | 2    | 라우터 mocking 필요                              |
| 구현 비용     | 2    | 작음                                             |

**YAGNI**: "아니오"에 가까움 — 이미 짧고 응집돼 있어 추출 이득이 적다. 보류.

### 후보 C — 본문 수정 로직을 전담 훅으로 추출

`isEditing`/`editedContent`/`isSaving` + 3개 핸들러(33줄)를 별도 훅으로 추출.

| 기준          | 점수 | 근거                                                                      |
| ------------- | ---- | ------------------------------------------------------------------------- |
| 변경 빈도     | 2    | 이력 없음                                                                 |
| 결함 위험     | 2    | 로직 단순                                                                 |
| 영향 범위     | 2    | 국지적                                                                    |
| 근거 강도     | 3    | Fact지만 이미 하나의 명확한 관심사로 응집되어 있어 "문제"라 부르기엔 약함 |
| 안전망 가능성 | 3    | 비교적 테스트하기 쉬움                                                    |
| 구현 비용     | 2    | 작음                                                                      |

**YAGNI**: "아니오"에 가까움 — 이미 응집도가 나쁘지 않다. 보류.

### 후보 D — 재생 트리거 정리

독립 후보로 두지 않는다 — 후보 A(UX 로그 훅)를 추출하면 `handlePlayFromPost`/`handlePlayAll`은 자연히 "재생 액션 호출 + 로그 훅에 곡 id 통지"로 단순해지는 하위 효과다.

### 후보 E — 컨테이너/표현 전면 분리(여러 서브컴포넌트로 쪼개기)

이번 Full 트랙에 포함하기엔 범위가 크다(YAGNI 관점에서 지금 8가지 책임을 한 번에 다 정리할 필요는 없음). 후보 A로 UX 로그를 먼저 걷어낸 뒤, 필요하면 별도 사이클로 재평가.

## 권장 후보

**후보 A(UX 로그 수집 훅 추출)를 권장합니다.** 근거 강도·결함 위험이 가장 높고, 파일에서 가장 큰 단일 응집도 문제이며, `useSwipeToDismiss`라는 이미 성공적으로 분리된 선례를 그대로 따라갈 수 있습니다. 후보 B·C는 이미 충분히 응집돼 있어 YAGNI 기준으로 보류합니다.

AI의 추천과 사용자의 최종 선택은 다를 수 있습니다. 다른 후보를 선택하시면 그 근거를 이 문서에 추가하겠습니다. 최종 선택권은 항상 사용자에게 있습니다.
