# 문제 영역

## 관찰한 증상

- `PostCardDetailModal.tsx`(396줄, `apps/web` 컴포넌트 중 최대)가 반응 상태(좋아요/댓글/본문수정) 반영 외에도 서로 다른 성격의 책임을 함께 담당한다: UX 로그 수집(체류 시간, 재생한 곡 추적, dwell 계산), 모바일↔데스크톱 리사이즈 시 프로필 페이지로의 라우팅 전환, 스와이프-투-디스미스 제스처 처리.
- `post-reaction-state` 리팩터링(#48) Stage 1 진단(`docs/refactors/post-reaction-state/diagnosis.md`, 후보 2)에서 이미 발견된 후보다. 근거 등급: 다중 관심사가 섞여 있다는 것 자체는 Fact(코드로 직접 확인)이지만, "이게 실제 문제를 일으켰다"는 근거는 Inference 수준으로 약하다고 평가됐다.

## 실제 사례

- 최근 100개 커밋 중 3회 변경된 hot spot(`diagnosis.md` 근거). 다만 변경 이유가 반응 상태뿐 아니라 여러 책임에 걸쳐 있어 "이 파일 자체가 병목"이라고 단정하기엔 근거가 약하다 — 이번 사이클에서 다시 확인이 필요하다.

## 초기 가설

- 하나의 컨테이너 컴포넌트가 "화면 조합"과 "서로 무관한 도메인 규칙(로깅, 라우팅, 제스처)"을 구분 없이 갖고 있어서 파일이 장황해졌다는 가설. 아직 검증되지 않았다(Hypothesis).

## 기대 효과

- 책임이 분리되면 각 관심사(로깅, 반응형 라우팅 전환, 스와이프 제스처, 반응 상태 표시)를 독립적으로 이해·수정·테스트할 수 있게 된다.

## 제약

- `post-reaction-state`(#48)에서 이미 좋아요 반응 상태 접근은 `usePostLikeToggle`/`usePostReactions`로 정리됐다 — 이번엔 그 외의 책임(UX 로깅, 반응형 라우팅, 스와이프 제스처)에 집중한다.
- `PostCardDetailModal`의 외부에서 관찰 가능한 동작(모달 열기/닫기, 좋아요/댓글/본문 표시, 모바일↔데스크톱 전환 시 라우팅, 스와이프로 닫기)은 변경하지 않는다.
