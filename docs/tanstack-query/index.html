VIBR 서버 상태 관리 아키텍처 — TanStack Query 도입 명세서

apps/web은 원래 서버 상태 캐싱 라이브러리 없이 각 화면이 useState+useEffect로 데이터를 개별 페칭했고, 무효화 전파는 zustand의 nonce/bump 스토어(usePlaylistRefreshStore, useFeedRefreshStore 등)가 수동으로 담당했습니다. 세 차례의 리팩터링 사이클(PR #148 → #177 → #184)을 거치며 이 역할이 전부 @tanstack/react-query(v5.101.3)의 queryKey 기반 캐시로 이관됐습니다. 이 문서는 "무엇이 왜 바뀌었는지"와 "지금 코드가 실제로 어떻게 동작하는지"를 하나로 묶어 설명합니다.

왜 도입했는가 — 구조적 원인이었던 6개 지점

CLAUDE.md는 "서버 상태와 UI 상태를 같은 종류로 취급하지 말라"고 명시합니다. 도입 전에는 이 원칙이 지켜지지 않아 무효화 전파가 "소비처가 관련 스토어를 빠짐없이 구독했는가"라는 사람이 지켜야 하는 수동 계약이었고, 실제로 이 계약이 최소 2곳에서 깨진 채 발견됐습니다.

핵심 개념 8가지

TanStack Query가 처음 도입되는 팀원이 이 저장소 코드를 읽기 전에 알아야 할 최소 개념 세트입니다. 각 카드는 저장소 안의 실제 사용례를 가리킵니다.

queryKey

캐시의 유일한 식별자. 배열이며 뒤에 변수를 붙여 항목별로 캐시를 격리한다(예: postId별로 다른 캐시). 키 설계 실수(변수 누락)는 서로 다른 데이터가 섞이는 사고로 직결되므로 이 저장소는 모든 키를 xxxQueryKey(...) 함수로 export해 오너십을 명확히 한다.

query-keys/post.ts:1 postDetailQueryKey(postId)

enabled

조건부로 쿼리 실행 자체를 끈다. 로그인 여부, 이미 데이터가 있는지(passedPost) 등을 반영해 불필요한 네트워크 호출을 원천 차단한다. staleTime이 있어도 enabled가 true면 첫 mount 시 fetch가 시도되므로 함께 낮춰야 한다(구현 중 실제로 발견된 함정).

usePostDetail.ts:40 enabled: enabled && Boolean(postId) && !matchedPost

staleTime

이 시간 안에는 같은 쿼리가 다시 mount돼도 재요청하지 않는다. 기본값은 0 — 0인 채로 두면 컴포넌트가 매번 새로 mount되는 화면(모달 열고 닫기 등)에서 캐시가 있어도 계속 재요청된다. authMe/postDetail 모두 pnpm dev 실동작 확인 중에야 이 함정을 실제로 재현하고서 추가했다.

useAuthMeQuery.ts:11 AUTH_ME_STALE_TIME_MS = 5분

invalidateQueries vs setQueryData

invalidateQueries는 "다음 기회에 다시 fetch해라"는 지연 무효화(플레이리스트 변경 후). setQueryData는 캐시를 즉시 직접 덮어써 네트워크 왕복 없이 반영한다(좋아요 수, 댓글 tmp-id 교체). updater가 undefined를 반환하면 no-op이라는 세부 동작이 댓글 롤백 설계를 바꾼 원인이었다.

usePostReactions.ts:96, 119

useMutation 3단 콜백

onMutate(낙관적 반영, 롤백용 스냅샷/tmp-id 기록) → onSuccess(서버 결과로 확정) → onError(실패 시 롤백). 항목 추가(댓글, tmp-id filter 방식)와 필드 갱신/교체(알림, snapshot-restore 방식)는 롤백 전략이 근본적으로 달라 공용 추상화로 묶지 않기로 결정됐다(사이클 ③ 참고).

useNotifications.ts:47-58, usePostReactions.ts:101-127

refetchInterval(함수형)

고정 숫자 대신 함수를 전달하면 매 스케줄링 시점마다 재평가된다. 댓글 폴링은 이 함수 안에서 컴포넌트 로컬 상태(입력 중인지, 뮤테이션이 진행 중인지)를 클로저로 참조해 false를 반환하는 방식으로 조건부 skip을 구현한다 — 이 저장소에 처음 도입된 패턴이라 회귀 테스트로 꼼꼼히 검증됐다.

usePostReactions.ts:133-137

useInfiniteQuery

getNextPageParam으로 다음 페이지 커서를 도출하고 fetchNextPage로 다음 페이지를 이어붙인다. 스크롤 트리거 배선(useInView) 자체는 데이터와 무관해 useInfiniteScrollTrigger 공유 훅으로 분리했다 — 5개 무한스크롤 화면이 이 훅 하나만 재사용한다.

FeedView.tsx:37-45, useInfiniteScrollTrigger.ts

QueryClientProvider 싱글턴

'use client' 컴포넌트로 ToastProvider와 동일한 패턴으로 app/layout.tsx를 감싼다. 모듈 스코프 싱글턴 QueryClient를 쓴다 — 서버 컴포넌트/SSR 하이드레이션 경계가 필요한 곳이 없어(모든 소비 훅이 'use client') 요청별 팩토리가 불필요했다.

components/providers/QueryProvider.tsx

export function useInfiniteScrollTrigger({ hasNextPage, isFetchingNextPage, fetchNextPage }: Params) {
  const { ref, inView: isInView } = useInView({ threshold: 0.8, rootMargin: '200px' });

  useEffect(() => {
    if (isInView && hasNextPage && !isFetchingNextPage) fetchNextPage();
  }, [isInView, hasNextPage, isFetchingNextPage, fetchNextPage]);

  return ref;
}

새 서버 데이터를 추가할 때 따라야 할 패턴

이 저장소에 새 API 연동 화면/기능을 추가한다면, 지금까지의 세 사이클이 만든 컨벤션은 다음과 같습니다.

  1. queryKey를 먼저 함수로 정의하고 src/query-keys/{'{'}domain{'}'}.ts에서 export한다. 문자열 배열을 직접 여러 곳에 하드코딩하지 않고, 훅/컴포넌트 파일에 로컬로 정의하지도 않는다 — xxxQueryKey(...) 형태로 도메인 파일에서 export(commentsQueryKey(postId) 등 참고. query-key-centralization 사이클 #209~#215에서 정착된 컨벤션).
  2. 목록/무한스크롤이면 useInfiniteQuery + useInfiniteScrollTrigger를 재사용한다. 새 스크롤 배선을 직접 구현하지 않는다.
  3. 다른 화면 변경이 이 데이터에 반영돼야 하면 invalidateQueries를, 네트워크 왕복 없이 즉시 반영해야 하면 setQueryData/setQueriesData를 쓴다. 새 zustand nonce/bump 스토어를 만들지 않는다.
  4. 폴링이 필요하면 refetchInterval을 쓴다. 조건부로 멈춰야 하면(입력 중 등) 숫자 대신 함수를 전달해 클로저로 조건을 반영한다.
  5. 낙관적 갱신이 필요하면 useMutation의 onMutate/onSuccess/onError 3단을 쓴다. 롤백 설계 전에 "이 mutation이 항목을 추가하는지, 필드를 갱신/교체하는지"부터 정한다 — 두 경우 롤백 전략(tmp-id filter vs snapshot-restore)이 다르다. setQueryData의 updater가 undefined를 반환하면 no-op이라는 점을 미리 감안한다.
  6. staleTime을 반드시 검토한다. 같은 화면이 반복 mount되는 경로(모달 열고 닫기 등)가 있다면 기본값 0으로는 캐시가 있어도 재요청이 발생한다 — 유닛 테스트만으로는 이 문제가 드러나지 않을 수 있으므로 pnpm dev 실동작으로 직접 확인한다.
  7. 서버 데이터를 zustand에 새로 담지 않는다. "여러 컴포넌트가 같은 서버 값을 봐야 한다"는 요구가 생기면 그 자체가 queryKey 캐시가 필요하다는 신호다(경계 원칙 참고).
