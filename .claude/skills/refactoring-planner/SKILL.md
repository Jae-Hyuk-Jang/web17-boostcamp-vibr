Mandatory human approval gates at every stage. # Refactoring Planner

코드 냄새나 막연한 개선 아이디어를 **근거가 있고, 동작을 보존하며, 되돌릴 수 있는 리팩터링 이슈**로 바꾸는 파이프라인입니다. 근거 문서는 `docs/refactors/refactoring-planning-workflow.md`이며, 이 스킬은 그 내용을 실행 가능한 절차로 옮긴 것입니다. 각 단계의 상세 배경이나 "왜 이 순서인가"가 궁금하면 그 문서를 직접 참고하세요. 문서에 채워 넣을 형식은 `references/templates.md`에 모아뒀습니다.

리팩터링은 "코드를 예쁘게 정리하는 작업"이 아니라 **다음 변경을 더 안전하고 빠르게 만들기 위해 현재 구조의 마찰을 줄이는 작업**입니다. 이 전제를 놓치면 파일 길이만 보고 근거 없이 쪼개거나, 새 라이브러리를 써보고 싶다는 이유로 구조를 통째로 바꾸는 실패로 이어집니다.

```
brief-original.md → [트랙 선택] → baseline.md → diagnosis.md → brief-fixed.md
    → plan.md → regression-plan.md → issues.md/GitHub Issues → result.md
```

## 시작하기 전에

`docs/refactors/{name}/brief-original.md`가 있어야 시작할 수 있습니다. `{name}`은 **해결책이 아니라 문제 영역**을 가리키는 kebab-case 슬러그입니다(좋은 예: `post-reaction-state`, `player-boundary` / 피할 예: `use-react-query`, `split-files` — 해결책을 이름에 넣으면 진단 전에 결론을 고정하게 됩니다).

파일이 없으면 **코드부터 고치지 말고 멈추세요.** `references/templates.md`의 최소 형식을 안내하고, 사용자가 관찰한 증상을 짧게라도 기록하도록 요청하세요. 스킬이 대신 문제를 지어내면, 사용자가 실제로 겪지 않은 문제를 해결하는 방향으로 파이프라인 전체가 잘못 진행됩니다.

각 단계는 **[GATE]**로 표시된 지점에서 사용자 승인 없이 다음 단계로 넘어가지 않습니다. 이 게이트들은 축약하거나 생략할 수 없습니다 — 구조 변경은 되돌리기 어려운 산출물(머지된 코드, 삭제된 이전 경로)을 만들기 때문에, 확인 없이 다음 단계까지 진행하면 잘못된 전제 위에 그 다음 단계가 쌓여서 되돌아가는 비용이 커집니다.

## 0. 트랙 선택 (Light / Full)

7단계 전체를 모든 리팩터링에 강제하면 기획 자체가 실제 작업량보다 무거워집니다. brief-original.md를 읽은 직후, 아래 기준으로 트랙을 정하고 사용자에게 어느 트랙으로 갈지 먼저 알리세요.

| 기준                           | Light 트랙              | Full 트랙                     |
| ------------------------------ | ----------------------- | ----------------------------- |
| 영향 범위                      | 단일 파일/모듈          | 여러 모듈·도메인·앱 경계      |
| 공개 계약(API, DTO, 화면 동작) | 불변                    | 변경 가능성 있음              |
| 라이브러리 도입                | 없음                    | 있음                          |
| 대안 비교 필요성               | 접근 방식이 사실상 하나 | 트레이드오프가 있는 복수 대안 |

네 기준이 모두 Light 쪽이면 Light 트랙, 하나라도 Full 쪽이면 Full 트랙입니다. 판단이 애매하면 Full을 기본값으로 하세요 — 과소평가해서 안전망 없이 진행하는 쪽이, 과대평가해서 문서를 조금 더 쓰는 쪽보다 위험합니다.

- **Full 트랙**: 아래 단계 1~5를 문서(`diagnosis.md`, `brief-fixed.md`, `plan.md`)까지 정식으로 작성.
- **Light 트랙**: 단계 1(진단)·2(목표 인터뷰)·3(3안 비교/ADR)의 정식 문서 작성은 생략하고, 그 결론(문제 원인 한두 문단, Goal/Out of Scope, 선택한 접근과 이유 한 문단)을 `brief-original.md`에 이어서 기록합니다. GATE 1·2·3도 생략하고 **GATE 0 → GATE 4 → GATE 5 → GATE 6** 순으로 진행합니다.

트랙과 무관하게 항상 지키는 것: **Behavior Invariants 기록, 최소 회귀 검증, 롤백 경로 명시.** 이 세 가지는 Light 트랙에서도 생략하지 않습니다 — 트랙 선택은 문서 작성량을 줄이는 것이지, 안전장치를 줄이는 것이 아닙니다.

## 단계 0: 범위와 기준선 고정

**목적**: 현재 동작과 품질 상태를 기록해서, "리팩터링 전에도 실패하던 것"과 "리팩터링이 새로 깨뜨린 것"을 구분할 수 있게 합니다.

**활동**:

1. `CLAUDE.md`, 관련 ADR·설계 문서(`docs/conventions.md`, `docs/design-system.md` 등), 패키지 매니페스트, 관련 코드와 테스트, 최근 커밋에서 반복적으로 변경된 파일 순으로 읽으세요. 기존 결정이 있다고 무조건 유지하지는 않되, 근거 없이 다시 논쟁하지도 마세요. 전제가 바뀌었거나 실제 문제가 확인된 경우에만 새 ADR로 대체합니다.
2. 관련 사용자 흐름, API 계약, 상태 전이, 데이터 저장 규칙에서 **Behavior Invariants**를 뽑아 기록하세요(형식은 `references/templates.md` 참고).
3. 기준 검증을 실행하세요: `pnpm lint`, `pnpm check-types`, `pnpm test`, `pnpm build`. **모든 명령이 성공한다고 가정하지 마세요** — 실행 결과, 실패 항목, 소요 시간을 있는 그대로 기록하세요. 특정 앱에 테스트 스크립트가 없다면 그것도 안전망 공백으로 적어두세요.
4. 가능하면 핵심 테스트 수/커버리지, 번들 크기·빌드 시간, 대상 API 응답 시간·쿼리 수, 변경 영향 파일 수 같은 지표도 수집하세요. 측정할 수 없는 값은 임의의 숫자를 만들지 말고 `측정 불가`와 이유를 쓰세요.

**산출물**: Full 트랙은 `docs/refactors/{name}/baseline.md`, Light 트랙은 `brief-original.md`에 최소 기준선만 인라인.

```
[GATE 0] 사용자가 대상 범위, 보존할 동작, 기준선의 기존 실패를 확인할 때까지 대기
```

## 단계 1: 비판적 구조 진단 (Light 트랙은 생략)

**목적**: "코드가 복잡해 보인다"는 인상을, 실제 변경 비용을 만드는 구조적 원인으로 좁힙니다.

**원칙**:

- **파일 길이는 증거가 아니라 탐색 신호입니다.** 긴 파일도 응집된 책임 하나를 갖는다면 나쁘지 않을 수 있고, 짧은 파일 여러 개가 암묵적 상태를 공유하면 더 나쁠 수 있습니다.
- **모든 판단에 근거 등급을 붙이세요**: Fact(코드·테스트·로그로 직접 확인) / Inference(여러 사실에서 도출한 해석) / Hypothesis(아직 검증하지 않은 가설). 가설을 사실처럼 쓰지 마세요.
- **증상과 근본 원인을 분리하세요**: 증상 → (왜?) → 직접 원인 → (왜?) → 구조 원인. 예: "좋아요 수정 때 피드와 상세 모달을 함께 손댄다" → "서버 상태와 화면별 낙관적 상태가 여러 위치에 존재한다" → "상태 소유권과 동기화 계약이 명시되지 않았다."

**탐색 항목**(후보를 찾을 때 훑을 체크리스트): 책임 응집도, 결합도, 상태 소유권 중복, 경계 명확성(UI/도메인/인프라가 섞였는가), 테스트 이음새, 오류·동시성 규칙의 분산, DTO/엔티티/화면 모델 역할 혼재, 운영성(로그·메트릭·롤백 지점), 변경 이력(자주 바뀌는 hot spot), 죽은 추상화(대체 구현 없이 래퍼만 늘어난 것).

**후보 우선순위**는 변경 빈도·결함 위험·영향 범위·근거 강도·안전망 가능성·구현 비용 6가지로 1~5점을 매기되, 총점만으로 자동 결정하지 말고 비교 근거로 쓰세요. **YAGNI 질문**: "이 영역에 향후 두세 번의 실제 변경이 없다면 지금 리팩터링할 가치가 있는가?" 답이 "아니오"면 보류 후보로 남기세요.

**산출물**: `docs/refactors/{name}/diagnosis.md` — 후보별 근거·우선순위·보류 이유, 선택을 권하는 후보 1개와 이유.

AI의 추천과 사용자의 최종 선택은 다를 수 있습니다. 사용자가 추천 후보와 다른 후보를 선택하면, 그 후보를 선택한 근거를 diagnosis.md에 추가로 기록한 뒤 다음 단계로 넘어가세요. 최종 선택권은 항상 사용자에게 있습니다.

```
[GATE 1] 사용자가 이번 사이클에서 다룰 문제 후보 하나를 선택할 때까지 대기
```

## 단계 2: 목표 인터뷰와 범위 확정 (Light 트랙은 생략)

**목적**: 선택한 구조 문제를 어떤 품질 속성까지 개선할지 확정합니다.

**방식**: 한 번에 질문 하나만 하고, 각 질문에 추천안과 이유를 포함하세요. 문서와 코드에 이미 답이 있으면 다시 묻지 마세요. 다뤄야 할 영역: ① 다음에 쉬워져야 할 구체적 변경, ② 절대 바뀌면 안 되는 사용자 동작/API 계약, ③ 가장 중요한 품질 속성(응집도/테스트성/성능/장애 격리/확장성 중 우선순위), ④ 허용 범위(단일 파일~공통 패키지), ⑤ 데이터 마이그레이션·배포 호환성 필요 여부, ⑥ 새 라이브러리 도입 허용 여부와 한계, ⑦ 성공 판단 기준(전후 지표/시나리오), ⑧ 명시적으로 하지 않을 것.

**산출물**: `docs/refactors/{name}/brief-fixed.md` — Goal, Success Criteria, Behavior Invariants(단계 0에서 확정한 것 재확인), Out of Scope.

```
[GATE 2] 사용자가 Goal, Success Criteria, Behavior Invariants, Out of Scope을 확정할 때까지 대기
```

## 단계 3: 3안 비교와 기술 결정 (Light 트랙은 생략)

**목적**: 한 해결책에 성급히 고정되지 않고, 비용·위험·효과가 다른 대안을 같은 기준으로 비교합니다.

**기본 대안 형태**(이름만 다른 세 안을 만들지 마세요): ① 최소 개선안 — 현재 패턴 유지, 책임·순수 함수·테스트 이음새만 정리, ② 경계 재설계안 — 도메인 모듈이나 상태 소유권을 재정의하고 점진적으로 이동, ③ 검증된 도구 도입안 — 라이브러리나 새 아키텍처 패턴으로 반복 책임을 위임. 라이브러리가 맞지 않으면 3안도 자체 구현안으로 제시할 수 있습니다 — "반드시 새 기술을 써야 한다"를 목표로 만들지 마세요.

**고정 비교 기준**(10개): 근본 원인 해결력, 동작 보존 난이도, 책임·의존성 변화, 테스트 용이성, 변경 범위, 점진적 전환 가능성, 롤백 가능성, 성능·운영 영향, 기존 코드와의 일관성, 유지 비용.

**라이브러리 도입 심사** (도입안이 있을 때만): 해결 책임과 라이브러리 핵심 추상화의 일치 여부, 현재 Next.js/React/NestJS/Node 버전 호환성, SSR/RSC/브라우저/서버 런타임 제약, 최근 릴리스·유지보수 상태, 라이선스·보안 이슈, 번들·런타임 비용, 제거 비용, 실제로 삭제되는 기존 코드/책임. "인기 많다", "요즘 많이 쓴다"는 도입 근거가 아닙니다.

**Spike 규칙**: 핵심 호환성·성능이 문서만으로 불확실하면 제품 코드를 바로 마이그레이션하지 마세요. 폐기 가능한 작은 spike로 한 가지(사용자 흐름 하나의 호환성, 상태 전이 하나의 표현 가능성, API 하나의 캐시/재시도 동작, 번들/응답 시간 영향)만 검증하고, spike 코드는 기본적으로 폐기한 뒤 관찰 결과만 plan.md에 남기세요.

**산출물**: `docs/refactors/{name}/plan.md` — 비교표 + ADR(형식은 `references/templates.md` 참고: Context/Decision/Alternatives/Consequences/Migration/Rollback).

```
[GATE 3] 사용자가 세 대안 중 하나를 선택하고 ADR·마이그레이션·롤백을 확정할 때까지 대기
```

## 단계 4: 회귀 안전망 설계

**목적**: 구조를 바꾸기 전에 현재 동작을 실행 가능한 테스트로 고정합니다. 트랙과 무관하게 항상 수행하되, Light 트랙은 최소 체크리스트로 축약합니다.

**테스트 우선순위**: ① Characterization test(현재 코드가 실제로 하는 일 고정) → ② Contract test(API/DTO/저장소/외부 서비스 경계 고정) → ③ State-transition test(낙관적 갱신, 롤백, 재시도, 큐 전이 고정) → ④ Integration test(여러 모듈이 합쳐지는 핵심 흐름) → ⑤ E2E test(사용자에게 중요한 소수 흐름). 모든 내부 구현을 스냅샷으로 얼리지 마세요 — 테스트는 바꿀 구조가 아니라 **보존할 동작**을 검증해야 합니다.

테스트를 쓰기 위한 최소 seam(시간·네트워크·저장소·난수 같은 외부 효과 주입, 큰 함수에서 순수 계산만 추출, 전역 접근을 얇은 adapter 뒤로 이동)은 허용하지만, 이 단계에서 새 구조 전체를 미리 구현하지는 마세요. "테스트 가능하게 만드는 최소 변경"만 별도 커밋으로 두세요.

**산출물**: Full 트랙은 `docs/refactors/{name}/regression-plan.md`(회귀 행렬 예시는 `references/templates.md` 참고) + 구현 전 추가할 테스트 목록. Light 트랙은 최소 회귀 체크리스트만.

```
[GATE 4] 사용자가 회귀 시나리오와 현재 안전망 공백을 확인할 때까지 대기
```

## 단계 5: 동작 보존 체크포인트로 이슈 분해

**목적**: 선택한 구조를 언제든 중단·검증·롤백할 수 있는 작은 작업으로 나눕니다.

Feature 이슈는 "사용자에게 보이는 수직 슬라이스"가 핵심이지만, Refactoring 이슈는 다른 질문을 씁니다: **"이 이슈만 머지해도 기존 동작이 유지되고 저장소가 정상 상태이며, 다음 이슈를 하지 않아도 되는가?"**

**권장 순서**: 특성화·계약 테스트 추가 → 최소 seam/새 경계 도입 → 핵심 규칙을 새 경계로 한 조각 이동 → 소비자를 하나씩 전환 → 전환 결과·운영 지표 확인 → 이전 경로와 dead code 제거 → 문서/ADR/전후 결과 갱신. **이전 코드는 새 경로의 동등성이 확인되기 전에 삭제하지 마세요.**

**이슈 크기**: 반나절~하루 안에 구현·검증 가능한 크기, 한 이슈에서 한 종류의 변화만, 대규모 rename·라이브러리 도입·상태 모델 변경을 한 번에 섞지 마세요. 각 이슈 종료 시 lint/type check/관련 test/필요 시 build가 통과해야 합니다.

**산출물**: `docs/refactors/{name}/issues.md`(템플릿은 `references/templates.md` 참고).

```
[GATE 5] 사용자가 각 이슈가 독립적으로 안전하고, 순서·검증·롤백이 구체적인지 확인할 때까지 대기
```

게이트를 통과하면 실제 이슈를 만드세요: `gh issue create --title "이슈 제목" --body "설명 + AC + 의존성"`. 프로젝트 보드 등록은 `gh project item-add <PROJECT_NUMBER> --owner <OWNER> --url <ISSUE_URL>`로 시도하되, `gh` 버전이 `gh project` 서브커맨드를 지원하지 않으면(버전 확인: `gh --version`, 2.20 미만이면 미지원) 무리하게 우회하지 말고 사용자에게 수동 등록을 안내하고 넘어가세요.

## 구현 단계 운영 규칙

기획이 끝난 뒤 각 이슈를 구현할 때는 다음을 지키세요.

**변경 전**: 해당 이슈의 Behavior Invariants와 Out of Scope을 다시 읽고, 작업 트리가 깨끗한지(또는 사용자 변경과 겹치는지) 확인하고, 관련 테스트가 기준선과 동일하게 동작하는지 확인하세요.

**변경 중**: 기계적 이동/rename과 동작 변경을 분리하고, 한 번에 한 소비자 또는 한 규칙만 전환하세요. 예상보다 변경 범위가 커지면 임의로 확장하지 말고 이슈를 다시 나누세요. 기존 실패를 리팩터링 성공으로 포장하지 마세요. 새 라이브러리의 추상화가 새는 경우 wrapper를 자동으로 추가하지 말고 경계 필요성을 다시 판단하세요.

**중단 조건** — 다음 중 하나가 발생하면 구현을 멈추고 plan.md를 재검토하세요: Behavior Invariant를 유지할 수 없음 / 데이터 마이그레이션이나 공개 API 변경이 새로 필요함 / 예상하지 못한 도메인까지 변경 범위가 확장됨 / 성능·번들·쿼리 수가 합의한 허용 범위를 벗어남 / 라이브러리 호환성·보안 전제가 틀림 / 롤백 경로가 사라짐.

## 완료 검증과 result.md

마지막 이슈가 끝나면 "코드가 컴파일된다"만 확인하지 마세요. 아래 영역을 비교하세요: 동작(모든 Behavior Invariants와 회귀 행렬 통과), 구조(선택한 책임 경계·의존 방향이 실제 코드에 반영됨), 품질(lint/type check/test/build 결과와 기존 실패 비교), 성능(합의한 렌더·응답·쿼리·번들 기준), 운영(로그·오류 처리·배포/롤백 가능성), 문서(ADR 상태·다이어그램·컨벤션 갱신). Light 트랙은 동작·품질 두 항목만 간단 요약하고 나머지는 해당 없음으로 표시할 수 있습니다.

**산출물**: `docs/refactors/{name}/result.md`(형식은 `references/templates.md` 참고).

```
[GATE 6] 사용자가 전후 비교와 남은 부채를 확인한 뒤 리팩터링 사이클을 종료
```

## VIBR 저장소 기본 규칙

VIBR은 `apps/web`, `apps/api`, `packages/dto`가 연결된 pnpm/Turborepo 모노레포입니다. 어느 단계에서든 다음을 기본값으로 삼으세요.

1. `packages/dto`의 계약 변경은 구조 변경으로 숨기지 말고 별도 검토하세요.
2. 프론트엔드의 서버 상태, UI 상태, 플레이어 상태를 같은 종류로 취급하지 마세요.
3. React 훅·컴포넌트는 줄 수가 아니라 책임과 상태 전이 수를 기준으로 분리하세요.
4. NestJS 서비스가 TypeORM 기본 Repository와 커스텀 Repository를 함께 쓸 때는, 일관성 자체보다 트랜잭션·쿼리 조합·테스트 이음새를 먼저 진단하세요.
5. Redis, Neo4j, MySQL을 오가는 변경은 장애 격리와 부분 실패 규칙을 baseline에 포함하세요.
6. `CLAUDE.md`가 특정 라이브러리를 쓰지 않는다고 명시했다면 몰래 도입하지 마세요. 실제 문제와 비교 근거가 있을 때만 새 ADR로 결정을 갱신하세요.
7. 프론트엔드 테스트 안전망이 부족한 영역은 구조 이동보다 특성화 테스트 도입을 먼저 이슈로 두세요.

## 승인 게이트 요약

| 게이트 | 확인 내용                                                     |
| ------ | ------------------------------------------------------------- |
| GATE 0 | 범위, Behavior Invariants, 현재 실패와 기준선                 |
| GATE 1 | 근거가 가장 강한 문제 후보 하나 선택 (Light 트랙은 생략)      |
| GATE 2 | Goal, Success Criteria, Out of Scope 확정 (Light 트랙은 생략) |
| GATE 3 | 3안 비교, ADR, 마이그레이션, 롤백 확정 (Light 트랙은 생략)    |
| GATE 4 | 특성화·계약·통합 테스트 안전망 확정                           |
| GATE 5 | 독립적으로 안전한 이슈와 실행 순서 확정                       |
| GATE 6 | 전후 효과, 회귀 여부, 남은 부채 확인                          |

Light 트랙은 GATE 0 → GATE 4 → GATE 5 → GATE 6만 거칩니다. 어느 트랙이든 이 게이트들에서는 실제로 멈추고 사용자의 응답을 기다리세요 — 스스로 "이 정도면 괜찮겠지"라고 판단하고 넘어가지 마세요. 게이트가 없으면 관찰하지 않은 문제를 해결하거나, 여러 구조 변경을 한 번에 수행하거나, 새 라이브러리 도입 자체를 성과로 오해하기 쉽습니다.
