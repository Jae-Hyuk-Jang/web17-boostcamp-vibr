# Refactoring Planner

코드 냄새나 막연한 개선 아이디어를 **근거가 있고, 동작을 보존하며, 되돌릴 수 있는 리팩터링 이슈**로 바꾸는 파이프라인입니다. 근거 문서는 `docs/refactors/refactoring-planning-workflow.md`이며, 이 스킬은 그 내용을 실행 가능한 절차로 옮긴 것입니다. 문서에 채워 넣을 형식은 `references/templates.md`에 모아뒀습니다.

리팩터링은 "코드를 예쁘게 정리하는 작업"이 아니라 **다음 변경을 더 안전하고 빠르게 만들기 위해 현재 구조의 마찰을 줄이는 작업**입니다. 이 전제를 놓치면 파일 길이만 보고 근거 없이 쪼개거나, 새 라이브러리를 써보고 싶다는 이유로 구조를 통째로 바꾸는 실패로 이어집니다.

```
brief-original.md → prd.md → adr.md → 구현 → result.md
```

산출 문서는 딱 3종입니다: **PRD**(문제 진단+목표), **ADR**(기술 결정+이슈 분해), **Result**(전후 비교+개발환경 실동작 확인). `brief-original.md`는 사용자가 직접 쓰는 짧은 입력 티켓이라 이 3종에 포함하지 않습니다. 규모와 무관하게 항상 이 세 문서와 세 게이트(GATE 1 → GATE 2 → GATE 3)를 모두 거칩니다 — 트랙 분기는 없습니다.

## 시작하기 전에

`docs/refactors/{name}/brief-original.md`가 있어야 시작할 수 있습니다. `{name}`은 **해결책이 아니라 문제 영역**을 가리키는 kebab-case 슬러그입니다(좋은 예: `post-reaction-state`, `player-boundary` / 피할 예: `use-react-query`, `split-files` — 해결책을 이름에 넣으면 진단 전에 결론을 고정하게 됩니다).

파일이 없으면 **코드부터 고치지 말고 멈추세요.** `references/templates.md`의 최소 형식을 안내하고, 사용자가 관찰한 증상을 짧게라도 기록하도록 요청하세요. 스킬이 대신 문제를 지어내면, 사용자가 실제로 겪지 않은 문제를 해결하는 방향으로 파이프라인 전체가 잘못 진행됩니다.

각 단계는 **[GATE]**로 표시된 지점에서 사용자 승인 없이 다음 단계로 넘어가지 않습니다. 이 게이트들은 축약하거나 생략할 수 없습니다 — 구조 변경은 되돌리기 어려운 산출물(머지된 코드, 삭제된 이전 경로)을 만들기 때문에, 확인 없이 다음 단계까지 진행하면 잘못된 전제 위에 그 다음 단계가 쌓여서 되돌아가는 비용이 커집니다.

## 단계 1: PRD — 비판적 진단과 목표 확정

**목적**: "코드가 복잡해 보인다"는 인상을 실제 변경 비용을 만드는 구조적 원인으로 좁히고, 그 원인이 왜 지금 다룰 가치가 있는지까지 확정합니다.

### 1-1. 기존 맥락 읽기

`CLAUDE.md`, 관련 ADR·설계 문서(`docs/conventions.md`, `docs/design-system.md` 등), 패키지 매니페스트, 관련 코드와 테스트, 최근 커밋에서 반복적으로 변경된 파일 순으로 읽으세요. 기존 결정이 있다고 무조건 유지하지는 않되, 근거 없이 다시 논쟁하지도 마세요. 전제가 바뀌었거나 실제 문제가 확인된 경우에만 새 ADR로 대체합니다.

### 1-2. 비판적 구조 진단 (시니어 개발자 시각)

이 절이 PRD의 핵심입니다 — 사용자가 brief-original.md에 적은 문제 제기를 그대로 받아 적지 말고, **경력 있는 엔지니어가 코드 리뷰에서 하듯 회의적으로 검증**하세요.

- **모든 판단에 근거 등급을 붙이세요**: Fact(코드·테스트·로그로 직접 확인) / Inference(여러 사실에서 도출한 해석) / Hypothesis(아직 검증하지 않은 가설). 가설을 사실처럼 쓰지 마세요.
- **증상과 근본 원인을 분리하세요**: 증상 → (왜?) → 직접 원인 → (왜?) → 구조 원인. 예: "좋아요 수정 때 피드와 상세 모달을 함께 손댄다" → "서버 상태와 화면별 낙관적 상태가 여러 위치에 존재한다" → "상태 소유권과 동기화 계약이 명시되지 않았다."
- **파일 길이는 증거가 아니라 탐색 신호입니다.** 긴 파일도 응집된 책임 하나를 갖는다면 나쁘지 않을 수 있고, 짧은 파일 여러 개가 암묵적 상태를 공유하면 더 나쁠 수 있습니다.
- **탐색 항목**(후보를 찾을 때 훑을 체크리스트): 책임 응집도, 결합도, 상태 소유권 중복, 경계 명확성(UI/도메인/인프라가 섞였는가), 테스트 이음새, 오류·동시성 규칙의 분산, DTO/엔티티/화면 모델 역할 혼재, 운영성(로그·메트릭·롤백 지점), 변경 이력(자주 바뀌는 hot spot), 죽은 추상화(대체 구현 없이 래퍼만 늘어난 것).
- **아키텍처 관점 질문**: 이 문제가 이 파일/모듈에만 있는가, 아니면 저장소 다른 곳에서도 반복되는 패턴인가? 기존 컨벤션(`CLAUDE.md`, `docs/conventions.md`)이나 이전 ADR과 충돌하는가? 지금 구조가 "당시엔 맞았지만 지금은 전제가 깨진" 결정인가, 아니면 애초부터 근거가 약했던 결정인가?
- **사용자 문제 제기 자체에 반박 질문을 먼저 던지세요**: "이 증상이 정말 구조 문제에서 오는가, 아니면 우연한 버그·일회성 실수인가?" "지금 안 고치면 다음 몇 번의 실제 변경에서 구체적으로 어떤 비용이 드는가(YAGNI: 향후 두세 번의 실제 변경이 없다면 지금 리팩터링할 가치가 있는가)?" "더 급한 다른 문제를 가리는 건 아닌가?" 이 질문들의 답을 PRD에 그대로 남기세요 — 사용자가 가져온 전제를 검증 없이 승인하는 것 자체가 이 단계의 실패입니다.
- 후보가 여럿이면 변경 빈도·결함 위험·영향 범위·근거 강도·안전망 가능성·구현 비용으로 간단히 우선순위를 매기되, 점수만으로 자동 결정하지 말고 비교 근거로 쓰세요.

### 1-3. 목표 인터뷰

**질문마다 `AskUserQuestion` 도구를 쓰세요** — 사용자가 매번 문장을 새로 타이핑하지 않고 방향키로 고를 수 있게 합니다. 문서와 코드에 이미 답이 있으면 다시 묻지 마세요. 서로 밀접하게 얽힌 질문(예: 마이그레이션 필요 여부 + 성공 판단 기준)은 한 번의 `AskUserQuestion` 호출에 최대 4개까지 묶을 수 있지만, 하나의 결정이 다음 질문의 전제가 되는 경우(예: 범위를 먼저 정해야 그 다음 질문이 의미가 있는 경우)는 답을 받은 뒤 다음 질문을 하세요.

**옵션 작성 규칙**:

- 추천하는 답을 첫 번째 옵션으로 두고 라벨 끝에 "(추천)"을 붙이세요(예: "안 2 — 지금은 도입 안 함 (추천)").
- 옵션 `description`은 **추천 이유를 줄바꿈으로 문단을 나눠** 쓰세요 — 한 문장으로 욱여넣지 말고, 무엇을 추천하는지와 왜 그런지를 시각적으로 구분합니다. 근거가 diagnosis 단계에서 나온 구체적 사실(Fact/Inference)이면 그 사실을 짧게 인용하세요.
- 대안 옵션에도 무엇이 달라지는지 한두 문장을 반드시 넣으세요 — "다른 방식"처럼 내용 없는 라벨만 두지 마세요.
- `AskUserQuestion`은 항상 "Other"(자유 입력)를 자동 제공하므로, 옵션에 없는 답을 강제로 옵션화하려 애쓰지 마세요.

다뤄야 할 영역: ① 다음에 쉬워져야 할 구체적 변경, ② 절대 바뀌면 안 되는 사용자 동작/API 계약, ③ 가장 중요한 품질 속성(응집도/테스트성/성능/장애 격리/확장성 중 우선순위), ④ 허용 범위(단일 파일~공통 패키지), ⑤ 데이터 마이그레이션·배포 호환성 필요 여부, ⑥ 새 라이브러리 도입 허용 여부와 한계, ⑦ 성공 판단 기준(전후 지표/시나리오), ⑧ 명시적으로 하지 않을 것.

코드에서 답이 바로 도출되는 항목(예: Behavior Invariants 후보)은 굳이 선택형 질문으로 만들지 말고, 도출한 내용을 먼저 제시한 뒤 "이대로 확정해도 될까요?" 형태의 단일 확인 질문만 `AskUserQuestion`으로 던지세요.

AI의 추천과 사용자의 최종 선택은 다를 수 있습니다. 사용자가 추천과 다른 선택을 하면 그 근거를 PRD에 추가로 기록한 뒤 다음 단계로 넘어가세요. 최종 선택권은 항상 사용자에게 있습니다.

### 1-4. 기준선 검증

`pnpm lint`, `pnpm check-types`, `pnpm test`, `pnpm build`를 실행하세요. **모든 명령이 성공한다고 가정하지 마세요** — 실행 결과, 실패 항목, 소요 시간을 있는 그대로 기록하세요. 특정 앱에 테스트 스크립트가 없다면 그것도 안전망 공백으로 적어두세요. 가능하면 핵심 테스트 수·커버리지, 번들 크기·빌드 시간, 변경 영향 파일 수 같은 지표도 수집하세요. 측정할 수 없는 값은 임의의 숫자를 만들지 말고 `측정 불가`와 이유를 쓰세요.

관련 사용자 흐름, API 계약, 상태 전이, 데이터 저장 규칙에서 **Behavior Invariants**를 뽑아 함께 기록하세요.

**산출물**: `docs/refactors/{name}/prd.md` — 문제 정의, 비판적 진단(근거 등급 포함), 목표/Success Criteria/Out of Scope, Behavior Invariants, 기준선 검증 결과.

```
[GATE 1] 사용자가 문제 진단, 목표·범위, Behavior Invariants, 기준선을 확인할 때까지 대기
```

## 단계 2: ADR — 기술 결정과 이슈 분해

**목적**: 한 해결책에 성급히 고정되지 않고 비용·위험·효과가 다른 대안을 같은 기준으로 비교하며, **그 결정에 이르는 과정 자체를 기록**해 나중에 "왜 이렇게 했는가"를 다시 물었을 때 근거를 찾을 수 있게 합니다.

### 2-1. 3안 비교

**기본 대안 형태**(이름만 다른 세 안을 만들지 마세요): ① 최소 개선안 — 현재 패턴 유지, 책임·순수 함수·테스트 이음새만 정리, ② 경계 재설계안 — 도메인 모듈이나 상태 소유권을 재정의하고 점진적으로 이동, ③ 검증된 도구 도입안 — 라이브러리나 새 아키텍처 패턴으로 반복 책임을 위임. 라이브러리가 맞지 않으면 3안도 자체 구현안으로 제시할 수 있습니다 — "반드시 새 기술을 써야 한다"를 목표로 만들지 마세요.

**고정 비교 기준**(10개): 근본 원인 해결력, 동작 보존 난이도, 책임·의존성 변화, 테스트 용이성, 변경 범위, 점진적 전환 가능성, 롤백 가능성, 성능·운영 영향, 기존 코드와의 일관성, 유지 비용.

**라이브러리 도입 심사** (도입안이 있을 때만): 해결 책임과 라이브러리 핵심 추상화의 일치 여부, 현재 Next.js/React/NestJS/Node 버전 호환성, SSR/RSC/브라우저/서버 런타임 제약, 최근 릴리스·유지보수 상태, 라이선스·보안 이슈, 번들·런타임 비용, 제거 비용, 실제로 삭제되는 기존 코드/책임. "인기 많다", "요즘 많이 쓴다"는 도입 근거가 아닙니다.

**Spike 규칙**: 핵심 호환성·성능이 문서만으로 불확실하면 제품 코드를 바로 마이그레이션하지 마세요. 폐기 가능한 작은 spike로 한 가지만 검증하고, spike 코드는 기본적으로 폐기한 뒤 관찰 결과만 남기세요.

### 2-2. 의사결정 인터뷰 로그 (신규 — 반드시 기록)

대안 사이에 실제로 갈리는 지점(예: 안 2 vs 안 3처럼 범위·비용이 뚜렷이 다른 선택)은 **1-3과 동일하게 `AskUserQuestion` 도구로 물으세요** — 대안 이름을 라벨로, 각 옵션 `description`에 "무엇이 달라지는가"와 "왜 이걸 추천하는가"를 줄바꿈으로 나눠 쓰고, 추천 대안에 "(추천)"을 붙입니다. 라이브러리 도입 여부처럼 이미 1-3 목표 인터뷰에서 결정된 항목은 ADR 단계에서 다시 묻지 말고, PRD의 해당 결정을 참조만 하세요.

`AskUserQuestion`으로 받은 질문·선택을 Q&A 형태로 adr.md에 그대로 옮기세요. 질문 텍스트는 실제로 물어본 문장 그대로, 답변은 사용자가 고른 옵션의 라벨과 그 근거(자유 입력을 골랐다면 입력한 내용)를 원문에 가깝게 남기세요 — 요약해서 뭉개지 마세요. 예:

```markdown
**Q. 안 2(공용 컴포넌트를 지금 위치에 추가)와 안 3(새 폴더 신설까지)의 차이가 핵심입니다. 이번에 폴더까지 신설할까요?**
A. 안 2 — 지금은 신설 안 함. 이유: 새 폴더 신설은 PRD가 Out of Scope로 뺀 "저장소 전역 구조 재정의"와 사실상 같은 작업이라 이번 사이클 범위(단일 도메인)와 충돌함.
```

이 로그가 있어야 ADR의 `Decision`이 "왜 그 순간에 그렇게 결정했는지"를 나중에도 추적할 수 있습니다.

### 2-3. 결정

**산출물**: `docs/refactors/{name}/adr.md`, 다음 섹션 포함(형식은 `references/templates.md` 참고):

- 비교표(10개 기준)
- 의사결정 인터뷰 로그
- ADR 본문: Context / Decision / Alternatives / Consequences / Migration / Rollback
- **회귀 안전망**(축약): Characterization → Contract → State-transition → Integration → E2E 순으로 우선순위를 매긴 테스트 목록과 최소 회귀 시나리오 표. 테스트를 쓰기 위한 최소 seam(시간·네트워크·저장소·난수 같은 외부 효과 주입, 큰 함수에서 순수 계산만 추출)은 허용하지만, 이 단계에서 새 구조 전체를 미리 구현하지는 마세요.
- **체크포인트 이슈 목록**: Feature 이슈는 "사용자에게 보이는 수직 슬라이스"가 핵심이지만, Refactoring 이슈는 "이 이슈만 머지해도 기존 동작이 유지되고 저장소가 정상 상태이며, 다음 이슈를 하지 않아도 되는가?"를 씁니다. 권장 순서: 특성화·계약 테스트 추가 → 최소 seam/새 경계 도입 → 핵심 규칙을 새 경계로 한 조각 이동 → 소비자를 하나씩 전환 → 이전 경로와 dead code 제거 → 문서 갱신. 이슈 크기는 반나절~하루, 한 이슈에서 한 종류의 변화만.

```
[GATE 2] 사용자가 대안 선택, 인터뷰 로그, ADR, 안전망, 이슈 분해를 확인할 때까지 대기
```

게이트를 통과하면 실제 이슈를 만드세요: `gh issue create --title "이슈 제목" --body "설명 + AC + 의존성"`. 프로젝트 보드 등록은 `gh project item-add <PROJECT_NUMBER> --owner <OWNER> --url <ISSUE_URL>`로 시도하되, `gh` 버전이 `gh project` 서브커맨드를 지원하지 않으면(버전 확인: `gh --version`, 2.20 미만이면 미지원) 무리하게 우회하지 말고 사용자에게 수동 등록을 안내하고 넘어가세요.

## 구현 단계 운영 규칙

기획이 끝난 뒤 각 이슈를 구현할 때는 다음을 지키세요.

**변경 전**: 해당 이슈의 Behavior Invariants와 Out of Scope을 다시 읽고, 작업 트리가 깨끗한지(또는 사용자 변경과 겹치는지) 확인하고, 관련 테스트가 기준선과 동일하게 동작하는지 확인하세요.

**변경 중**: 기계적 이동/rename과 동작 변경을 분리하고, 한 번에 한 소비자 또는 한 규칙만 전환하세요. 예상보다 변경 범위가 커지면 임의로 확장하지 말고 이슈를 다시 나누세요. 기존 실패를 리팩터링 성공으로 포장하지 마세요. 새 라이브러리의 추상화가 새는 경우 wrapper를 자동으로 추가하지 말고 경계 필요성을 다시 판단하세요. `packages/dto`를 수정했다면 다음 확인 전에 반드시 `pnpm dto`부터 다시 실행하세요.

**중단 조건** — 다음 중 하나가 발생하면 구현을 멈추고 `adr.md`를 재검토하세요: Behavior Invariant를 유지할 수 없음 / 데이터 마이그레이션이나 공개 API 변경이 새로 필요함 / 예상하지 못한 도메인까지 변경 범위가 확장됨 / 성능·번들·쿼리 수가 합의한 허용 범위를 벗어남 / 라이브러리 호환성·보안 전제가 틀림 / 롤백 경로가 사라짐.

## 단계 3: 완료 검증과 result.md

마지막 이슈가 끝나면 "코드가 컴파일된다"만 확인하지 마세요. 아래 영역을 비교하세요: 동작(모든 Behavior Invariants와 회귀 시나리오 통과), 구조(선택한 책임 경계·의존 방향이 실제 코드에 반영됨), 품질(lint/type check/test/build 결과와 기존 실패 비교), **개발환경 실동작**, 성능(합의한 렌더·응답·쿼리·번들 기준), 운영(로그·오류 처리·배포/롤백 가능성), 문서(ADR 상태·컨벤션 갱신).

### 개발환경 실동작 확인 (필수, 사용자에게 위임 금지)

정적 검증(lint/type-check/build)이 전부 통과해도 dev 서버에서만 재현되는 런타임 에러가 있을 수 있습니다 — 실제로 이 저장소에서 배럴 import 정리 후 `pnpm dev`에서만 "module factory is not available" 에러가 반복 재현된 사례(PR #84)가 있었고, 같은 커밋에서 테스트 mock 경로 충돌로 CI가 실패한 사례도 있었습니다. 정적 검증만으로 "동작한다"고 결론 내리지 마세요.

1. `packages/dto`를 변경했다면 **가장 먼저** `pnpm dto`를 실행해 재빌드하세요.
2. `run` 스킬이 있으면 그것을 사용해 앱을 기동하고 변경된 화면/흐름을 직접 조작해 확인하세요. 없으면 `pnpm dev`로 dev 서버를 직접 백그라운드로 띄우고, 로그에 컴파일·런타임 에러가 없는지, 변경된 라우트·API가 정상 응답하는지(`curl` 등)까지는 반드시 직접 확인하세요.
3. "이 환경에서 확인 불가"라고 쓰고 사용자에게 통째로 떠넘기는 것은 최후의 수단입니다. 그 경우에도 어디까지 직접 확인했고 무엇을 못 했는지(예: 시각적 레이아웃 확인만 브라우저가 필요해 못 함) 구체적으로 남기고, 남은 부분만 사용자에게 요청하세요.

### Before/After

baseline.md 대신 prd.md의 기준선 검증 결과와 비교해, **구체적으로 무엇이 달라지고 개선됐는지** 수치·구조·테스트 기준으로 명시하세요("깔끔해졌다" 같은 모호한 서술 금지).

**산출물**: `docs/refactors/{name}/result.md`(형식은 `references/templates.md` 참고): 변경 요약, Before/After, 개발환경 실동작 확인 결과, Behavior Verification, Decision Review(선택한 안의 예상과 실제 비교), Remaining Debt, Follow-ups.

```
[GATE 3] 사용자가 전후 비교, 개발환경 실동작 확인, 남은 부채를 확인한 뒤 리팩터링 사이클을 종료
```

## VIBR 저장소 기본 규칙

VIBR은 `apps/web`, `apps/api`, `packages/dto`가 연결된 pnpm/Turborepo 모노레포입니다. 어느 단계에서든 다음을 기본값으로 삼으세요.

1. `packages/dto`의 계약 변경은 구조 변경으로 숨기지 말고 별도 검토하고, 변경 후 `pnpm dto`로 반드시 재빌드하세요.
2. 프론트엔드의 서버 상태, UI 상태, 플레이어 상태를 같은 종류로 취급하지 마세요.
3. React 훅·컴포넌트는 줄 수가 아니라 책임과 상태 전이 수를 기준으로 분리하세요.
4. NestJS 서비스가 TypeORM 기본 Repository와 커스텀 Repository를 함께 쓸 때는, 일관성 자체보다 트랜잭션·쿼리 조합·테스트 이음새를 먼저 진단하세요.
5. Redis, Neo4j, MySQL을 오가는 변경은 장애 격리와 부분 실패 규칙을 baseline에 포함하세요.
6. `CLAUDE.md`가 특정 라이브러리를 쓰지 않는다고 명시했다면 몰래 도입하지 마세요. 실제 문제와 비교 근거가 있을 때만 새 ADR로 결정을 갱신하세요.
7. 프론트엔드 테스트 안전망이 부족한 영역은 구조 이동보다 특성화 테스트 도입을 먼저 이슈로 두세요.
