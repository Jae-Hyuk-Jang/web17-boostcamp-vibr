# 문서 템플릿

각 단계에서 작성하는 문서의 최소 형식입니다. SKILL.md 본문에서 해당 단계에 도달했을 때 이 파일을 참조하세요.

## brief-original.md 최소 형식 (사용자 입력, 파이프라인 시작 전제)

사용자에게 아직 이 파일이 없다면 아래 형식을 채워달라고 요청하세요.

```markdown
# 문제 영역

## 관찰한 증상

- 어떤 변경이 어렵거나 반복적으로 실패하는가?
- 어느 파일·모듈·사용자 흐름에서 나타나는가?

## 실제 사례

- 최근 수정·버그·중복·성능 문제의 구체적 예

## 초기 가설

- 원인으로 의심하는 것은 무엇인가?
- 확정 사실이 아니라 가설임을 명시한다.

## 기대 효과

- 이 구조를 개선하면 어떤 다음 변경이 쉬워지는가?

## 제약

- 반드시 유지할 동작, 일정, 호환성, 운영 제약
```

## Behavior Invariants 예시

```markdown
## Behavior Invariants

- 로그인하지 않은 사용자의 공개 피드 접근 결과는 바뀌지 않는다.
- 좋아요 요청 실패 시 화면과 전역 상태가 이전 값으로 복구된다.
- 큐에서 현재 곡을 제거할 때 적용되는 다음 곡 선택 규칙은 유지된다.
- 기존 DTO의 필드명과 optional/nullable 의미는 유지된다.
```

## prd.md 형식 (단계 1, GATE 1)

```markdown
# PRD — {name}

## 문제 정의

- brief-original.md 요약
- 왜 지금 다뤄야 하는가

## 비판적 진단 (시니어 개발자 시각)

### 근거

- Fact / Inference / Hypothesis로 등급을 붙여 나열

### 증상 → 원인 체인

증상 → (왜?) → 직접 원인 → (왜?) → 구조 원인

### 아키텍처 관점

- 이 문제가 이 모듈에 국한되는가, 저장소에 반복되는 패턴인가?
- 기존 컨벤션/이전 ADR과 충돌하는가?
- 전제가 깨진 결정인가, 애초에 근거가 약했던 결정인가?

### 비판적 재검토 (사용자 문제 제기에 대한 반박 질문과 답)

- 이 증상이 정말 구조 문제인가, 우연한 버그인가?
- 지금 안 고치면 다음 몇 번의 변경에서 구체적으로 어떤 비용이 드는가? (YAGNI)
- 더 급한 다른 문제를 가리는 건 아닌가?

### 후보 우선순위 (후보가 여럿일 때만)

| 후보 | 변경 빈도 | 결함 위험 | 영향 범위 | 근거 강도 | 안전망 가능성 | 구현 비용 | 선택/보류 |
| ---- | --------- | --------- | --------- | --------- | ------------- | --------- | --------- |

## 목표와 범위

## Goal

## Success Criteria

## Out of Scope

## Behavior Invariants

(위 예시 형식)

## 기준선 검증

| 명령             | 결과 | 실패 항목 | 비고 |
| ---------------- | ---- | --------- | ---- |
| pnpm lint        |      |           |      |
| pnpm check-types |      |           |      |
| pnpm test        |      |           |      |
| pnpm build       |      |           |      |

측정 가능하면: 테스트 수/커버리지, 번들 크기·빌드 시간, 변경 영향 파일 수. 측정 불가한 값은 "측정 불가"와 이유를 남긴다.

---

**[GATE 1]** 위 진단·목표·범위·Behavior Invariants·기준선을 확인해주시면 다음 단계로 넘어가겠습니다.
```

## adr.md 형식 (단계 2, GATE 2)

````markdown
# ADR — {name}

## 3안 비교

### 안 1 — 최소 개선안

### 안 2 — 경계 재설계안

### 안 3 — 검증된 도구 도입안 (또는 대안 자체 구현안)

## 비교표 (10개 고정 기준)

| #   | 기준                 | 안 1 | 안 2 | 안 3 |
| --- | -------------------- | ---- | ---- | ---- |
| 1   | 근본 원인 해결력     |
| 2   | 동작 보존 난이도     |
| 3   | 책임·의존성 변화     |
| 4   | 테스트 용이성        |
| 5   | 변경 범위            |
| 6   | 점진적 전환 가능성   |
| 7   | 롤백 가능성          |
| 8   | 성능·운영 영향       |
| 9   | 기존 코드와의 일관성 |
| 10  | 유지 비용            |

## 라이브러리 도입 심사 (도입안이 있을 때만)

해결 책임-핵심 추상화 일치, 버전 호환성, 런타임 제약, 유지보수 상태, 라이선스/보안, 번들/런타임 비용, 제거 비용, 삭제되는 기존 코드.

## 의사결정 인터뷰 로그

질문-답변을 요약해서 뭉개지 말고, 결정을 좌우한 답변은 원문에 가깝게 남긴다.

```markdown
**Q. (핵심 기술 질문)**
A. (사용자 답변) 이유: (사용자가 밝힌 근거)
```
````

## 선택: 안 N

왜 이 안을 선택했고 다른 안을 왜 기각했는지, 비교표 근거를 다시 요약.

## ADR 본문

### Context

어떤 구조 문제와 제약 때문에 결정이 필요한가?

### Decision

무엇을 선택하고 어느 범위에만 적용하는가?

### Alternatives

거부한 대안과 각각의 거부 이유는 무엇인가?

### Consequences

장점, 단점, 새로 생기는 위험과 운영 비용은 무엇인가?

### Migration

어떤 순서로 옮기며 중간 상태는 어떻게 동작하는가?

### Rollback

어떤 신호가 나오면 중단하고 어디까지 되돌리는가?

## 회귀 안전망

### 테스트 우선순위

Characterization → Contract → State-transition → Integration → E2E 순으로, 이번 사이클에서 추가할 테스트 목록.

### 회귀 시나리오

| 시나리오      | 기존 결과           | 검증 수준 | 실패 시 조치        |
| ------------- | ------------------- | --------- | ------------------- |
| 정상 요청     | 응답·화면 상태      | 통합      | 구현 중단           |
| 네트워크 실패 | 롤백·메시지         | 상태 전이 | 구현 중단           |
| 중복 요청     | 중복 방지/멱등 결과 | 계약      | 설계 재검토         |
| 빈 값·경계값  | 현재 예외/기본값    | 단위      | 동작 변경 이슈 분리 |

## 체크포인트 이슈 목록

이슈마다 아래 형식을 반복.

```markdown
# 목적

이 체크포인트가 줄이는 구조적 위험은 무엇인가?

## Scope

- 수정할 경계와 파일

## Out of Scope

- 이번 이슈에서 하지 않을 일

## Behavior Invariants

- 반드시 유지할 외부 동작

## Acceptance Criteria

- [ ] Given [기존 조건], When [동일한 행동], Then [기존과 동일한 결과]
- [ ] Given [실패/경계 조건], When [행동], Then [정의된 롤백/예외 결과]
- [ ] 새 구조의 책임과 의존 방향이 adr.md의 결정과 일치한다.

## Verification

- [ ] 실행할 테스트·lint·type check·build 명령

## Rollback

- 되돌릴 커밋/flag/adapter와 데이터 호환 조건

## Dependency

- 선행 이슈와 후속 이슈
```

## result.md 형식 (단계 3, GATE 3)

```markdown
# Result — {name}

## 변경 요약

무엇을 어떤 경계로 옮겼는가? 이슈별 요약.

## Before / After

prd.md의 기준선 검증과 비교해 **구체적으로 무엇이 달라지고 개선됐는지** 수치·구조·검증 결과로 명시. 모호한 서술("깔끔해졌다") 금지.

| 항목 | Before(prd.md 기준선) | After |
| ---- | ---------------------- | ----- |

## 개발환경 실동작 확인

- `packages/dto` 변경 여부와, 변경했다면 `pnpm dto` 재빌드 실행 결과
- 앱 기동 방법(`run` 스킬 / `pnpm dev`)과 실제로 확인한 화면·흐름·API
- dev 서버 로그에 컴파일/런타임 에러가 없었는지
- 직접 확인하지 못한 부분이 있다면 무엇을, 왜 못 했는지, 사용자가 무엇을 마저 확인하면 되는지

## Behavior Verification

보존한 동작과 테스트 증거. prd.md의 Behavior Invariants와 adr.md의 회귀 시나리오를 각각 짚어 통과 여부를 밝힌다.

## Decision Review

adr.md에서 선택한 안의 예상 장점·비용과 실제로 드러난 차이.

## Remaining Debt

의도적으로 남긴 문제와 다시 검토할 조건.

## Follow-ups

별도 feature, bug-fix, 추가 리팩터링 후보.

---

**[GATE 3]** 위 Before/After, 개발환경 실동작 확인, Behavior Verification, 남은 부채를 확인해주시면 이 리팩터링 사이클을 종료하겠습니다.
````
