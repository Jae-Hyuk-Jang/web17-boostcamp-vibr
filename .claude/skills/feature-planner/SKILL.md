# Feature Planner

새 기능을 "아이디어"에서 "개발 가능한 이슈 단위"로 바꾸는 3단계 파이프라인입니다. 근거 문서는 `docs/features/feature-planning-workflow.md`이며, 이 스킬은 그 내용을 실행 가능한 절차로 옮긴 것입니다. 상세한 배경이나 이유가 궁금하면 그 문서를 직접 참고해도 됩니다.

```
spec-original.md (초기 아이디어)
    ↓ 단계 1 — 요구사항 인터뷰
spec-fixed.md (확정된 요구사항)
    ↓ 단계 2 — PRD 작성 + 기술 결정(ADR)
prd.md (단일 기준 문서)
    ↓ 단계 3 — 이슈 분해
issues.md + GitHub Issues (실행 가능한 작업 단위)
```

## 시작하기 전에

`docs/features/{name}/spec-original.md`가 있어야 시작할 수 있습니다. `{name}`은 기능을 가리키는 kebab-case 슬러그(예: `tag-system`)이고, 사용자가 대화에서 언급하지 않았다면 먼저 물어보세요.

파일이 없으면 **인터뷰를 시작하지 말고 멈추세요.** 이 워크플로우는 사용자가 이미 다듬어본 초기 아이디어를 전제로 설계됐습니다 — 스킬이 대신 아이디어를 지어내면 사용자가 실제로 원하지 않는 방향으로 인터뷰가 진행될 위험이 큽니다. `docs/features/{name}/spec-original.md`를 먼저 작성해달라고 요청하세요.

각 단계는 **[GATE]**로 표시된 지점에서 사용자 승인 없이 다음 단계로 넘어가지 않습니다. 이 워크플로우 전체가 여러 세션에 걸쳐 진행될 수 있는 무거운 작업이기 때문에, 게이트 없이 끝까지 달리면 사용자가 확인하지 못한 채로 잘못된 방향의 문서/이슈가 쌓입니다. 각 게이트에서 명시적으로 멈추고, 사용자의 응답을 받은 뒤에만 계속하세요.

---

## 단계 1: 요구사항 인터뷰

**목적**: 초기 기능 정의서의 모호성을 제거하고, 엣지 케이스와 결정 사항을 확정합니다.

**입력**: `docs/features/{name}/spec-original.md`, 그리고 코드베이스(기존 구조·패턴을 참조하기 위해 관련 영역을 먼저 탐색하세요).

**활동**: spec-original.md와 코드베이스를 읽은 뒤, 구현 전에 확인이 필요한 것들을 **한 번에 하나씩** 질문하세요. 질문마다 추천 방식을 이유와 함께 제시하세요 — 사용자가 매번 처음부터 판단하지 않고, 제안에 동의/수정하는 방식으로 빠르게 결정할 수 있게 하기 위함입니다. 아래 8가지 영역을 다루되, spec-original.md에 이미 명확히 답이 있는 항목은 다시 묻지 마세요:

1. 이 기능의 primary user는 누구인가?
2. 최소 동작 시나리오 3개는? (가장 기본적인 사용 흐름)
3. 데이터 저장 방식 — 기존 구조와의 관계는?
4. 경계 조건 — 최대값, 빈 값, 중복, 동시성은?
5. 에러 처리 — 실패 시 사용자에게 어떻게 표시하는가?
6. 기존 UI 패턴과의 일관성 — 어떤 컴포넌트를 재사용할 수 있는가?
7. 성능 제약 — 허용 응답 시간, 데이터 크기 제한은?
8. 향후 확장 가능성 — 이 결정이 다음 feature에 영향을 주는가?

**Ubiquitous Language 정의**: 인터뷰 중 반복적으로 쓰이는 용어를 그 자리에서 고정하세요. 코드·문서·대화에서 같은 단어가 같은 것을 가리키게 하는 것이 목적이며, 나중에 PRD·이슈·코드에서 용어가 흔들리면 구현자가 매번 다시 해석해야 합니다. 확정된 용어는 spec-fixed.md에 "용어 정의" 섹션으로 남기세요.

**산출물**: `docs/features/{name}/spec-fixed.md`

```
[GATE] 사용자가 spec-fixed.md를 읽고 확정할 때까지 대기
```

## 단계 2: PRD 작성 + 기술 결정(ADR)

**목적**: 요구사항·디자인·기술 결정·범위를 하나의 문서로 통합해서, "이 기능에 대해 궁금하면 여기만 보면 된다"는 단일 기준점을 만듭니다.

**입력**: `docs/features/{name}/spec-fixed.md`, `docs/features/{name}/design.md`(있으면), 코드베이스.

### 2-1. PRD 뼈대 생성

기술 결정 섹션은 2-3에서 채우므로 TODO로 비워둔 채 먼저 구조를 잡으세요.

- **개요** — 기능의 목적과 범위
- **사용자 스토리** — 사용자 관점의 흐름
- **기술 결정** — 어떤 구조 위에 올릴 것인가 (2-3에서 ADR로 채움)
- **Out of Scope** — 이번에 하지 않을 것 (2-4에서 작성)
- **용어 정의** — spec-fixed.md의 Ubiquitous Language를 그대로 가져와 동기화

### 2-2. 아키텍처 3안 제안 & 비교

최소 3가지 구현 방식을 스스로 제안하고, 아래 7가지 고정 기준으로 비교표를 만드세요. 기준을 고정하는 이유는, 안마다 다른 잣대로 비교하면 사용자가 "사과와 오렌지"를 비교하게 되어 선택이 어려워지기 때문입니다.

| #   | 기준                 | 설명                                           |
| --- | -------------------- | ---------------------------------------------- |
| 1   | 데이터 구조          | 어떤 형태로 데이터를 저장/표현하는가           |
| 2   | API 레이어 변경지점  | 기존 API에서 무엇이 바뀌는가                   |
| 3   | 상태관리 변경지점    | Context/Store에서 무엇이 추가되는가            |
| 4   | 핵심 동작            | 이 기능의 가장 중요한 동작이 어떻게 구현되는가 |
| 5   | 컴포넌트 구조        | 어떤 컴포넌트가 추가/수정되는가                |
| 6   | 기존 패턴과의 일관성 | 코드베이스의 기존 관습과 얼마나 맞는가         |
| 7   | 테스트 용이성        | 단위/E2E 테스트 작성이 쉬운가                  |

```
[GATE] 사용자가 3안 중 하나를 선택할 때까지 대기
```

### 2-3. 선택한 안을 ADR 4요소로 "기술 결정" 섹션에 작성

```markdown
### 기술 결정 제목

**Context** — 이 결정이 필요한 맥락. 무엇을 풀고 있는가.
**Decision** — 무엇을 선택했는가.
**Alternatives** — 거부한 안과 각각의 거부 이유. 이유 없는 거부는 쓰지 마세요 —
나중에 "왜 이 안을 안 썼더라"를 다시 물어야 하면 ADR을 쓰는 의미가 없습니다.
**Consequences** — 트레이드오프. 장점뿐 아니라 단점도 반드시 명시하세요.
```

### 2-4. Out of Scope 작성

"하지 않을 것"을 구체적으로 나열하세요. 이 항목이 AI에게 특히 중요한 이유는, 명시하지 않으면 구현 단계에서 맥락을 확장 해석해 범위를 초과하기 쉽기 때문입니다(예: "태그" 기능을 만들면서 요청하지 않은 "태그 색상 커스터마이징", "태그 자동 추천", "태그 기반 검색"까지 손대는 식). 애매하면 일단 Out of Scope에 적어두는 쪽이 안전합니다.

```
[GATE] 사용자가 Out of Scope을 읽고 확정할 때까지 대기
```

**산출물**: `docs/features/{name}/prd.md`

## 단계 3: 이슈 분해

**목적**: PRD를 독립적으로 TDD 사이클을 돌릴 수 있는 실행 단위(GitHub Issues)로 변환합니다.

**입력**: `docs/features/{name}/prd.md`, GitHub 프로젝트 보드(있으면).

### 수직 슬라이싱 원칙

이슈를 쪼갤 때마다 스스로에게 물으세요: **"이 이슈만 완료하면 사용자에게 보여줄 수 있는 동작이 있는가?"**

- Yes → 수직 슬라이스. TDD 사이클(Red→Green→Refactor)을 이슈 단위로 돌릴 수 있습니다.
- No → 다른 이슈와 합치거나 다시 나누세요.

레이어별 수평 슬라이싱(API → Context → UI 순으로 이슈를 나누는 것)은 하지 마세요. 마지막 이슈까지 완료해야 눈에 보이는 동작이 나오기 때문에, 중간 이슈 단계에서는 TDD의 "Green"을 확인할 방법이 없습니다.

### 이슈 크기와 순서

- 반나절~하루 안에 TDD 사이클을 완료할 수 있는 크기로 자르세요. 너무 크면 피드백 루프가 느려지고, 너무 작으면 PR 오버헤드(리뷰, CI, 머지)가 실제 작업량을 넘어섭니다.
- 앞 이슈의 결과가 다음 이슈의 입력이 되도록 의존성 순서를 배치하세요. 역방향 개발(뒷 이슈를 먼저 구현해야 앞 이슈가 의미 있어지는 순서)은 피하세요.

### Acceptance Criteria

각 이슈에 Given-When-Then 형식으로 AC를 반드시 포함하세요. 이 AC는 이후 테스트 시나리오 작성 단계의 씨앗이 되므로, 여기서 모호하게 쓰면 그 단계에서 다시 되짚어야 합니다.

```markdown
## Acceptance Criteria

- [ ] Given [사전 조건], When [행동], Then [기대 결과]
- [ ] Given [사전 조건], When [행동], Then [기대 결과]
```

```
[GATE] 사용자가 이슈 목록을 읽고 수직 슬라이스 기준 충족을 확인할 때까지 대기
```

### GitHub 등록

게이트를 통과하면 실제 이슈를 만드세요:

```bash
gh issue create --title "이슈 제목" --body "설명 + AC + 의존성"
```

프로젝트 보드 등록은 `gh project item-add <PROJECT_NUMBER> --owner <OWNER> --url <ISSUE_URL>`로 시도하되, 이 저장소의 `gh` CLI 버전이 `gh project` 서브커맨드를 지원하지 않을 수 있습니다(버전 확인: `gh --version`, 2.20 미만이면 미지원). 실패하면 무리하게 우회하지 말고 사용자에게 "프로젝트 보드는 수동으로 등록해달라"고 안내하고 넘어가세요 — 이슈 생성 자체는 이미 성공했으니 그것까지 막을 필요는 없습니다.

**산출물**: `docs/features/{name}/issues.md`, GitHub Issues(각 이슈에 AC 포함), 가능하면 프로젝트 칸반 보드 Todo 컬럼.

## 승인 게이트 요약

| 지점        | 확인 내용                                         |
| ----------- | ------------------------------------------------- |
| 단계 1 후   | spec-fixed.md — 모호성 제거, 용어 확정            |
| 단계 2-2 후 | 3가지 안 비교 — 사용자가 안을 선택함              |
| 단계 2-4 후 | Out of Scope — 범위 확정                          |
| 단계 3 후   | 이슈 목록 — 수직 슬라이스, AC 구체성, 의존성 순서 |

이 게이트들을 건너뛰면 안 되는 이유는, 이 워크플로우 전체가 되돌리기 어려운 산출물(공개된 GitHub 이슈, 팀이 참조할 PRD)을 만들기 때문입니다. 사용자가 확인하지 않은 채로 다음 단계까지 진행하면, 잘못된 전제 위에 그 다음 단계가 쌓여서 되돌아가는 비용이 커집니다. 게이트에서는 실제로 멈추고 사용자의 응답을 기다리세요 — 스스로 "이 정도면 괜찮겠지"라고 판단하고 넘어가지 마세요.
